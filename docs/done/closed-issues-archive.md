| ~~SD write throughput~~ | ✅ **RESOLVED 2026-09-20 — and the "BCM2711 controller quirk" was ours.** DMA writes were disabled for years' worth of commits on the grounds that "a write-DMA quirk on this controller" corrupted them. Root cause: the driver programmed the engine a **raw CPU-physical address**, while `bcm2711.dtsi` declares `dma-ranges = <0x0 0xc0000000 0x0 0x0 0x40000000>` for the emmc2bus — bus `0xC0000000+X` maps CPU-phys `X`. Linux applies that translation, and so do `rpi4-audio` (`DRAM_BUS()`) and the kernel (`dtb_armToBus()`); **the SD driver was the only DMA master in the tree skipping it**. ⊕ The recorded symptom was wrong too: corruption was whole-transfer and every time, not "first block, ~1-2/10". **ADMA2 32-bit scatter-gather is now the data path for both directions** — the engine Linux actually runs on this silicon (no in-tree driver programs SDHCI SDMA on a BCM2711). Measured end-to-end (`/usr/bin/dd` from an NFS-hosted image, 64 MiB, engine confirmed in each boot log): **PIO 12.2 · SDMA 12.3 · ADMA2 12.7–12.9 MB/s** — the SD bus bounds all three at this transfer size, so the win is architectural (no 512 KiB request cap, no contiguous-buffer requirement) rather than raw MB/s. ⚠ That is an end-to-end figure and is **not** comparable with the older raw-driver ~17 MB/s number, which was measured differently. | C2 (2026-09-23) | **A userspace process with a `SIGSEGV` handler installed can silently wedge the whole kernel by exhausting its stack.** `hal_cpuPushSignal()` (`hal/aarch64/cpu.c`) writes the signal frame to the user stack with an unconditional `hal_memcpy` onto `signalCtx->sp`, then `hal_stackPutArgs` below it, and always returns 0 so the caller cannot decline. No locking and no printing in the guard: `vm_mapBelongs()` takes a mutex and `lib_printf` from the scheduler self-deadlocks. Kernel `560d1727`, manifest `2026-09-23-c2-signal-frame-guard.md`. | P6 (2026-09-24) | **`echo > file` from a shell script was ~50x slower than `dd` on real storage — and the cause was one missing `else` in libphoenix `setvbuf()`.** ✅ **RESOLVED** (libphoenix `008e25d`, tests `6e7a7f6`). `setvbuf()` cleared `stream->buffer`, then only re-allocated it inside `else if (old_siz != size)`. With no matching `else`, a request for the size the stream ALREADY had fell through leaving `bufsz = 4096` and `buffer == NULL` — and `fwrite_unlocked()` opens with `if (stream->buffer == NULL) { /* unbuffered write */ }`. The stream was permanently unbuffered: one `write()` syscall per call, and per *character* for `putchar()`, since `vprintf` feeds a char at a time (unlike `vfprintf`, which stages into 256 bytes). ★ **Not a corner case:** `fopen` always allocates `BUFSIZ`, and `setlinebuf(s)` is `setvbuf(s, NULL, _IOLBF, 0)` whose 0 is rewritten to `BUFSIZ` just above — so the sizes ALWAYS matched, and the standard line-buffering idiom silently *unbuffered* every stream it touched. bash does this to stdout at startup; psh's own `top` was hit identically. On ext2 each resulting write is a 12.5 ms appending write, so 513 bytes of `echo` cost 6.4 s — measured 6.4 s/file, exact. ⭑ **The measurement that cracked it, after several wrong turns:** same bytes, same directory, different writer — builtin `echo` 32 s/5 files, builtin `printf` 32 s, **external `/usr/bin/echo` 1 s**, `dd` 0 s. Same target rules out the filesystem; two different builtins rule out the builtin, leaving their shared `stdout`. Controls agreed: a **1-byte** payload on the same ext2 cost 0 s (only the payload changed), and tmpfs/`/dev/null` were ~0 s for the same 512 bytes — so cost = syscall count x per-write cost, not bash CPU. ⛔ *Why it hid:* every earlier attempt to exonerate libphoenix used a `fopen`'d file, which never calls `setvbuf` — the path that works. And all six pre-existing `stdio_bufs` tests pass a *caller* buffer, taking the `buffer != NULL` branch, so the NULL-buffer path real ports use had **zero** coverage. ✔ **Gate:** 3 new `stdio_bufs` cases proven red first (9 Tests 3 Failures) then green (0 Failures); full stdio (94) and printf (133) suites clean; bash relinked and hash-verified (`dd404338`→`36514daa`, since it is `--enable-static-link` and a libphoenix rebuild alone does NOT touch it); benchmark re-run: builtin `echo` **32 s → 0 s**, matching the external baseline, with output size still 513 bytes. ➡ **Wider than bash:** any port calling `setlinebuf()` or `setvbuf(..., NULL, ...)` has been running unbuffered, so this is a system-wide small-I/O win. Two adjacent ownership bugs fixed in the same block: an equal-size `_IONBF` request (e.g. `setbuf(s, NULL)`) leaked the old buffer, and a replaced buffer inherited stale `bufpos`/`bufeof`. ⚠ **Still open, separately:** the ext2 appending write costs 12.5 ms vs 169 us for an in-place overwrite; deferring `ext2_sb_sync()` to unmount/sync (Linux behaviour) is worth ~1.5x and is not filed as its own row. |
