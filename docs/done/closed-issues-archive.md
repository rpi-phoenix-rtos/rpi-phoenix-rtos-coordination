| P6 (2026-09-24) | **`echo > file` from a shell script was ~50x slower than `dd` on real storage — and the cause was one missing `else` in libphoenix `setvbuf()`.** ✅ **RESOLVED** (libphoenix `008e25d`, tests `6e7a7f6`). `setvbuf()` cleared `stream->buffer`, then only re-allocated it inside `else if (old_siz != size)`. With no matching `else`, a request for the size the stream ALREADY had fell through leaving `bufsz = 4096` and `buffer == NULL` — and `fwrite_unlocked()` opens with `if (stream->buffer == NULL) { /* unbuffered write */ }`. The stream was permanently unbuffered: one `write()` syscall per call, and per *character* for `putchar()`, since `vprintf` feeds a char at a time (unlike `vfprintf`, which stages into 256 bytes). ★ **Not a corner case:** `fopen` always allocates `BUFSIZ`, and `setlinebuf(s)` is `setvbuf(s, NULL, _IOLBF, 0)` whose 0 is rewritten to `BUFSIZ` just above — so the sizes ALWAYS matched, and the standard line-buffering idiom silently *unbuffered* every stream it touched. bash does this to stdout at startup; psh's own `top` was hit identically. On ext2 each resulting write is a 12.5 ms appending write, so 513 bytes of `echo` cost 6.4 s — measured 6.4 s/file, exact. ⭑ **The measurement that cracked it, after several wrong turns:** same bytes, same directory, different writer — builtin `echo` 32 s/5 files, builtin `printf` 32 s, **external `/usr/bin/echo` 1 s**, `dd` 0 s. Controls agreed: a **1-byte** payload on the same ext2 cost 0 s (only the payload changed), and tmpfs/`/dev/null` were ~0 s for the same 512 bytes — so cost = syscall count x per-write cost, not bash CPU. ⛔ *Why it hid:* every earlier attempt to exonerate libphoenix used a `fopen`'d file, which never calls `setvbuf` — the path that works.
