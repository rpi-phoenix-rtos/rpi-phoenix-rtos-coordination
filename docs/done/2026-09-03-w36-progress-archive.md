- **★★★★★ THE REGRESSION IS EXPLAINED, and it reconciles both readings: a latent unlocked-submit race was EXPOSED by a threading change on 09-01.** The chain, every link evidenced:
  1. **The winsys has never had any submit serialization** — no mutex, no atomics — around `phoenix_v3d_ioctl`, which programs shared V3D MMIO (CT0/CT1/CSD queues, MMU, cache control) *and* mutates global BO/VA/page-table state.   4. **Result:** the interleaving changed and the always-present race began to manifest — CSD dispatches racing into a unit that holds only one CURRENT + one QUEUED (hence `status=0x7`, pileup, 14 timeouts, presentation frozen at frame 26), and plausibly also #67's "GPU executing image data" (two concurrent submits pairing one job's `rcl_start` with another's buffer).

- **★★★★★ ROOT CAUSE of the present stall (bug #2), decoded from the register and confirmed in the code: a timed-out CSD dispatch is never cleared, so every later dispatch queues behind it forever.** Decoded `status=0x00000007` against Linux's own `v3d_regs.h` (`V3D_CSD_STATUS_*`): **`HAVE_QUEUED_DISPATCH=1`, `HAVE_CURRENT_DISPATCH=1`, `NUM_ACTIVE=1`, `NUM_COMPLETED=0`** — i.e. at timeout a dispatch is *in flight* and **another is already queued behind it**. Then in `ioc_submit_csd()`: on timeout it prints, clears `INT_CSDDONE`, flushes caches and **`return 0`** — **no reset, no drain, and success reported**. So the first stuck dispatch stays `current` forever, every subsequent CSD piles up behind it (**14 timeouts per bad boot**), and presentation jams permanently at **present #26** while the engine keeps rendering. That is the whole ~3/8 "capture flake", explained end to end.
  - **Also found, and bigger:** the winsys has **no serialization at all** — no mutex, no atomics — around `phoenix_v3d_ioctl`, which programs shared V3D MMIO (CT0/CT1/CSD queues, MMU, cache control) *and* mutates global state (BO table, VA allocator, page table). On Linux this cannot happen: the kernel driver locks and the DRM scheduler serializes per queue. Worth testing whether this also explains **#67** — two concurrent submits interleaving register programming would pair one job's `rcl_start` with another's buffer, which is *exactly* the "GPU executing image data" signature.
  - **Fix (after Phase 2, then measured, not asserted):** on CSD timeout, drain/reset the CSD instead of returning success, and refuse to kick while `HAVE_CURRENT_DISPATCH` is set. Baseline to beat is known: **3/8 boots stall**; a real fix drives that to 0 over n≥8.

- **★★★ AF_UNIX "bytes that were never sent": ROOT CAUSE FOUND, fix implemented (HW test pending).** Not memory corruption at all — **socket ids were recycled**. `unix_bind` publishes a filesystem node whose identity is `{US_PORT, socket id}`; `close()` removes nothing (POSIX-correct — the name lives until `unlink()`, and `unix_unlink` is a no-op stub); but `unixsock_alloc` handed out the **lowest free id**, so a freed id returned at once. `unix_connect`/`send` resolve a pathname to an oid and then `unixsock_get(oid.id)` — which handed them a **different, live socket**, and `send` wrote the payload into *its* buffer. - **★★ `open()` race in the kernel FIXED + MEASURED (found by the heap audit, not by the crash).** `posix_open` has to publish `p->fds[fd].file` **before** filling the file in — the slot is how the fd is reserved across its three blocking IPCs — and then dropped `p->lock`, so a half-built `open_file_t` was reachable from every other thread of the process with `refs`/`oid`/`type` still holding recycled garbage.
