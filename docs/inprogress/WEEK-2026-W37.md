### 3e. ★★★ ROOT-CAUSED A REAL libc BUG — `strncmp` read one byte past `n`

Chasing the STK corruption turned up something bigger. STK faulted early this cycle, and the fault
symbolised to **libphoenix `strncmp`**, not to STK:

```
Exception #36: Data Abort (EL0)  esr=0x92000007  far=0x0cf0e000
x0=0x0cf0dfff  x2=0x1        pc -> strncmp (string/string.c:109)
                             lr -> asCTokenizer::IsKeyWord(char const*, ...)
```

`esr` WnR is clear, so it is a **read**: `n=1`, `s1` the **last byte of a mapped page**. The relink
did not *cause* this — it **exposed** it: shifting allocation sizes moved a script buffer so that it
now ends exactly at a page boundary. That is why earlier runs reached lap 1/2, and why the answer is
this fix rather than a rollback. Both
`strncmp` and `strncasecmp` looped on `*p && k < n`, and C evaluates left to right — so the byte at
index `n` is dereferenced **before** the bound is tested. Reading one byte too far is invisible until
that byte is the first of an unmapped page, which is why it presented as an *intermittent* crash.
`strncpy`/`stpncpy`/`strncat` in the same file already order the bound first; only these two were
inverted, and **`strncasecmp` had no test coverage at all.**

Fix libphoenix **`f2d2789`**, test phoenix-rtos-tests **`a82e0e4`**. Verified three ways: the
built `libphoenix.a` disassembly checks `n` before every load (`cbnz x2` ahead of `ldrb [x0]`); a
host A/B with the second of two mapped pages unmapped shows the old loop faulting and the new one
returning 0; and the new loop's sign matches the system libc on 66 in-bounds cases. The new test
maps two pages and **unmaps** the second — `mprotect` is best-effort here, so a `PROT_NONE` page that
stayed readable would pass vacuously.

⚠ This is **not** yet shown to be the previously-known intermittent STK crash — two of that row's
four fault PCs were inside the allocator, so at least those are something else. But `strncmp` is
used by everything, so this is a candidate for intermittent faults well beyond STK.
