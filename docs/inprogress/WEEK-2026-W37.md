## 2b. ✅ YOUR BUG #5 — mechanism CONFIRMED by measurement; same defect as bug #2

Three probes cleared every candidate path (`glamor_spans` 0 hits · `glamor_copy` 1 copy in a whole
session, neither side the screen pixmap · the readback always `y0=0 rows=1080 H=1080`, a uniform
whole-screen flip). A fourth, at the decision itself, found the cause:

**There are TWO full-screen render targets, and both are classified as "the scanout."**
```
rsc #1  1920x1080  rt=1  -> create_flags=0x2      <-- gets the framebuffer's pages
rsc #4  1920x1080  rt=1  -> create_flags=0x2      <-- gets fresh DRAM, but STILL Y_0_TOP
```
The test is `(bind & PIPE_BIND_RENDER_TARGET) && width >= 1024 && height >= 768` — a **size
heuristic standing in for scanout identity**, applied independently in `v3d_resource.c:143` and
`st_atom_framebuffer.c:137`. The winsys refuses the second claim so the pages are never shared, but
nothing stops the `Y_0_TOP` forcing applying to **both** — so the second RT renders with an inverted
viewport, and through the uniform whole-screen flip that is exactly a mirror. One such resource would
have refuted this; two confirm it. **#5 is bug #2's defect, not a separate bug.**

⚠️ **The fix I proposed last turn is withdrawn.** `PIPE_BIND_SCANOUT` is **never set** here
(`scanout_bind=0` on all nine resources), so keying off it would have compiled, changed nothing, and
cost a Pi cycle plus a re-gate to discover. `v3d_bo`'s `bool scanout` is no better — it is set from
the *request*, so both RTs carry it. Measuring before fixing is what caught this.

**Next, cheapest first:** only the winsys knows which BO really got the scanout pages, and consulting
it crosses the st↔driver boundary — so first establish **why there are two full-screen RTs at all**.
If the second is avoidable, the symptom goes with no new plumbing. ⚠️ Then owner-gated (expires the
6-app gate). Analysis doc §10–§11.

## 4. WHAT GOT DONE THIS WEEK (short)
**★★ STK was capped at exactly 1 fps by a broken C++ clock — fixed, now 5.84 fps (5.8×).** libstdc++ here
has **no** time backends, so `std::chrono::steady_clock` falls back to `std::time()` — whole-**second**
ticks; the per-port patch reads `CLOCK_MONOTONIC` (`ports 6f08c26`). `docs/misc/2026-09-08-stk-frame-budget.md`.

**⚠️ YOUR CALL — the general fix.** A **toolchain** defect: all C++ `std::chrono` timing here has 1-second
granularity and fails *silently* elsewhere. Fix = rebuild libstdc++ with `--enable-libstdcxx-time=rt`
(`steady_clock::now()` is in `libstdc++.a`, so no header define helps) — whole-system C++ rebuild, **not**
started unattended.
