## 2c. ⚠ NEW, and you should know before you flash: quitting the desktop wedges the Pi ~1 in 6

The exit soak had only ever been run on the **pre-relink** build. Re-run on the shipped binaries:
**1 of 6 observed session exits hung the board.** In the bad run the kernel printed
`vm: page fault with a corrupt process pointer` (`vm/map.c:892`) and then produced **no further
output at all** — the shell prompt never came back and two later commands went unanswered. The other
5 exits shut down cleanly. Gameplay and the desktop *while running* are unaffected.

What it is: `thread->process` pointing at a **freed** `process_t`. `process_isLive()` only tests
`magic == PROCESS_MAGIC`, and `process_destroy()` clears that magic immediately before `vm_kfree(p)`
(`proc/process.c:122`) — so this fires on a plain **use-after-free**, not on the "wild-written" memory
the code comments assume. It is **not new today**: the scheduler carries the *same* check at
`proc/threads.c:534`, so the condition has been hit before and was papered over with a printf and a
fallback to the kernel map in two places rather than fixed. Killing six clients at once (what
quitting Window Maker does) is what makes it likely.

**★ The WEDGE is now root-caused, and the cause is the kernel's own safety net.** Two proven defects,
both independent of whatever corrupts the pointer:

1. The scheduler's "name the victim" diagnostic (`proc/threads.c:539`) calls `lib_printf` **while
   holding `threads_common.spinlock`** — and `lib_printf` → `lib_putch` → `log_write` takes
   `log_common.lock`, whose acquisition re-enters `hal_spinlockSet(&threads_common.spinlock)`
   (`threads.c:1833`), a **non-recursive** spinlock, with the global scheduler lock held and
   interrupts masked. **The first character deadlocks the CPU**, then every other core wedges at its
   next scheduler entry. That is why no `proc: thread …` line ever appears, and why the `vm:` message
   stops mid-word: a timer tick lands inside the byte-at-a-time print. Two runs truncated at 8 and 34
   characters — a fixed bug would truncate in the same place.
2. The `proc = NULL` fallback **guarantees a panic**: `vm_mapForce(kmap, <user addr>)` can only fail,
   and the failure branch is `LIB_ASSERT_ALWAYS(proc != NULL, "exception in kernel")` — with `proc`
   just set to NULL. Under `NDEBUG` that reaches `hal_cpuReboot()`, which on BCM2711 is
   `for (;;) hal_cpuHalt()`. **No reboot, permanent halt.**

Reproduced 2 of ~12 exits. The dangling pointer itself is **not** a `process_t` refcount hole — a
full census of all 13 `refs` sites and every thread-exit path found the accounting symmetric; the
leading candidate is a stray write into a recycled `thread_t` (there is a root-caused precedent on
this board at `threads.c:343`). `thread->process` is also written **once** (`threads.c:700`) and never
cleared, so any freed process leaves it dangling forever.

**✅ Landed this turn (kernel `ac40dcf1`, pushed, HW-verified):** the same fault class kills the kernel
at `_kmalloc_free` → `lib_listRemove`. All three zone `LIST_REMOVE` sites now check both links point
into kernel space and **strand** the zone instead of faulting. Boots, runs the desktop, exits cleanly,
and **does not false-positive**. Manifest `manifests/2026-09-09-kmalloc-zone-link-guard.md`.
⚠ My first version of that patch had a deadlock of exactly the kind described above (printing under
the allocator's own non-recursive mutex, which `log_write` re-enters via `vm_kmalloc`); it now uses
`hal_consolePrint`, the HAL's documented leaf lock.

**✅ FIXED (kernel `ce445804`, pushed):** all three diagnostics now format with `lib_sprintf` and emit
with `hal_consolePrint` (the HAL's leaf lock, allocation-free), capped at 4 lines; the fallback retires
just the faulting thread instead of asserting into a permanent halt; both detection sites clear
`thread->process`; and `process_dumpException` no longer follows a non-live pointer. The scheduler line
now also prints `magic`/`refs`, which tells us **which** cause it is next time it fires (`magic==0` +
`refs==0` = a real `process_t` use-after-free; arbitrary bits = a stray write).

**Soak: 20/20 clean session exits, 0 wedges, 0 faults** (5 cycles × 4 exits). At the observed ~1-in-6
base rate, 20 clean exits by luck is `(5/6)^20` ≈ **2.6%**, so the wedge is gone with ~97% confidence.

⚠ **But one honest gap, and it is the reason I am not calling this closed:** **no diagnostic fired in
any of the 20 runs**, so the *corruption* did not happen either — which means the new recovery path
(retire the thread, keep the board alive) is **still unexercised on hardware**. And a null result right
after a code change is exactly the trap this project already hit once: the 2026-09-02 pass found that
adding a `memset` perturbed the timing enough to stop the corruption reproducing. So "20/20 green"
may partly be "the bug hid again".

**★ Recovery path now DEMONSTRATED, not inferred** (test-only injection, compiled out of shipped
builds — verified 0 `INJECT` strings in `loader.disk`). Pointing a thread at a `process_t` with `magic`
cleared to 0 (exactly what `process_destroy` leaves) shows:

- the diagnostic printed **complete** — both real wedges truncated it mid-word, at 8 and 34 characters.
  That is the direct evidence the print path no longer deadlocks the CPU.
- the discriminator works: **`magic=00000000 refs=0`**, so the next real occurrence will say whether it
  is a genuine use-after-free or a stray write.

boot, so it retired a thread of an essential early process and that run never reached a prompt. That is

It also exposed a real defect in my own previous commit: the "NOT LIVE" line went only to `posix_write`,

## 2d. 🔎 OPEN: the AF_UNIX liveness failure is a DOUBLE FREE in the forked child

Root-caused from data already captured. `test-libc-unix-socket` fails ~1 iteration in 50 of
`accept_connect_liveness`: the forked child hits a **double free**, libphoenix's allocator detects it
and calls `_exit(EX_SOFTWARE)` — and `EX_SOFTWARE` is **70**, which is the "unexplained" exit code the
parent reported via `WEXITSTATUS`.

**I got this wrong last turn and the correction matters:** I wrote that "no code path in that test
exits 70". True of the test — but the exit came from **libphoenix**, and `Double free detected` was
sitting in the log immediately above the assertion. I had not grepped for the allocator's own message.

What the allocator's own structure already tells us: the branch *above* this one catches a smashed
header and leaks the block instead. Reaching the double-free branch means `malloc_chunkValid()`
**passed** — the header is self-consistent with its heap and only the in-use bit is clear. So this is
a genuine double free, not a corrupted header.

**Done this turn:** the report used to be the bare string `Double free detected` with no context, which
is why it took a session to interpret. It now names the block — `ptr`, `size`, `heap`, and the heap's
`size`/`freesz` — matching the corrupt-header path's style (libphoenix, force-relinked because
`test-libc-*` misses the `libphoenix.a` dependency). A rate + block-identity run is in flight.

**★ It is NOT a double free — the named report settled that immediately.** With the block identified,
the numbers are self-refuting: `ptr=0x25e0`, `heap=0x2000`, `hsize=0x1000`. Those are page-2
addresses; no mmap'd user heap lives there, and `0x25e0` looks like an *offset* rather than a pointer.
So the child called `free()` on a **garbage pointer**, the allocator derived a header from low memory
that happened to look self-consistent, found the in-use bit clear, and called it a double free.
`malloc_chunkValid()` passed because a fabricated header can satisfy it.

That points at libc teardown on an inherited heap — which is exactly what this test file's own
pre-existing instrumentation was built for (a heap canary carried across the fork, and a check for the
stdio `FILE *` globals being zeroed after fork). Neither fired, but the stdio check only tests the
three globals, not the contents of the `FILE` structs they point at. Next: validate the freed pointer
against the heap set before trusting the header, and dump the child's `FILE` structs at exit.

**Rate:** did not reproduce in 350 liveness iterations (200 isolated + 150 in full-suite runs), then
recurred once when a desktop session ran first in the same boot. So my earlier "~1 in 50" was wrong.

## 2e. ✅ FIXED: the desktop could fault the KERNEL 2982 times via `top`

A run with the desktop up produced **2982 identical EL1 Data Aborts** (`far=0x1`, `hal_strlen`,
called from `process_getName`): one `argv` slot held the value `1`, and `top` re-enumerates every
process on each refresh, so it faulted on every tick. The register dump carried the Game-of-Life
xterm's command line, naming the victim.

Three bugs in that one function, all fixed (kernel `3c8009b7`): `argv` entries were dereferenced
without validation (they are one kernel `vm_kmalloc` block, so a non-kernel address is impossible);
the loop had **no bound** on `argc`, so a missing NULL terminator walks off the array; and
`*(sbuf - 1) = '\0'` ran unconditionally, writing **one byte before the caller's buffer** when
`argv[0]` was NULL. HW: 0 faults, storm gone, desktop exits clean.

⚠ The corrupt `argv` itself is not fixed — `proc_copyargs` allocates from the same 128-byte class as
the zone headers in the heap-corruption work order, so this is very likely another victim of that
class. This commit stops a userspace-triggerable kernel abort, not the corruption.
