## 4. WHAT GOT DONE THIS WEEK (short)

**★ SuperTuxKart in-game is NOT blocked — corrected.** `stk --race-now --track=hacienda
--numkarts=3` reaches a real race over netboot, **0 faults** — Hacienda dirt track, race timer,
minimap, opponents, full lighting and HUD. Screenshot-quality.

**⚠️ Its frame rate: every number I gave you before today was wrong. Retracted.** I reported
~0.35 fps, then ~1.0 fps. Both came from broken metrics. The real figure, from STK's own frame
counter, is **≥5.6 fps at 1080p with a driven kart** — marginal, but 16x better than what I
reported and recognisably a running game.

* `mpdecimate` unique-frame counting was **confounded**: under `--race-now` the player kart gets
  no throttle and never leaves the start line, so frames differ only in the clock digits and
  score as duplicates.
* Race-clock advance rate was **saturated**: it read 0.97–1.02 fps for four different runs
  including one STK itself measured at 5.617 fps (5.8x low), and the clock froze outright for
  16 s in one. It is pinned near 0.05 s/s and carries no frame-rate information.
* **Use `stk --profile-time=N`** for all future STK perf work: `ProfileWorld` prints
  `Number of frames: … Average FPS: …` to the UART, and drives the kart with AI so the scene
  actually moves. It is a lower bound (load time is in the denominator, its frames are not in
  the numerator).

Consequences: **"not fill-rate bound" is withdrawn and stays withdrawn.** I re-ran the A/B on
the valid metric and it looked confirmed (1080p 1326 frames/236.055 s vs 640x480 1326
frames/236.329 s — 0.12% apart). It is void: I verified STK *accepted* `--screensize=640x480`,
not that it *rendered* there. `phxgl: scanout FBO(s)` reads **1920x1080 in both runs** — the
scanout FBO is bound to `/dev/fb0`'s native mode, so the "window" *is* the display and a
window-size request cannot reach the render target. Identical frame counts were the tell.
Varying render resolution needs a **framebuffer mode change** (mailbox / `config.txt` /
`rpi4-fb`) or render-to-smaller-FBO-and-blit — not a flag. Per-frame cost is ~178 ms; what it
consists of is **unknown**. Confirm resolution from `phxgl: scanout FBO(s) <W>x<H>`, never from
STK's "You choose to use". **Audio refuted** as the cost. Kart-count independence stands (that used the same run-to-run comparison but was never the
basis for an absolute claim). Full detail:
`docs/misc/2026-09-08-stk-framerate-measurement-void.md`.

**Fixed:** `stk-launcher` silently ignored every caller option (`697cd21a3`). It appended user
args after its own and assumed "later wins"; STK's `CommandLine` *rejects* a duplicate, and
rejects it **non-fatally**, so `--screensize=640x480` was accepted on the command line and the
game ran at 1080p anyway. HW-verified: `invalid_param=0`, STK logs "You choose to use 640x480."

**New crash, not on the demo path:** `--profile-time` prints its report, then takes a Data Abort
(EL0) formatting the per-kart table — `esr=0x92000044` (write, translation fault L0), `far` and
x4/x5 hold a 16-bit ascending sequence dereferenced as a pointer, with a stack-range line printed
just before. Stack exhaustion is the first suspect. `--no-sound` normal-mode run did not crash.
