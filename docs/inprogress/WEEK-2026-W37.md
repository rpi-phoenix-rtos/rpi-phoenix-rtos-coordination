## 3d. ★★★ NOT AUDIO — a HEAP BASE is getting into a free bin

The widened report ran on hardware and **overturned my own audio hypothesis**. The one field that
settles it is `heap = 0x0`: `malloc_chunkInit()` sets `->heap` on every chunk it makes, so an entry
with a NULL heap **is not a chunk**. Reading the same bytes as a `heap_t` header plus its first
chunk makes every field consistent — `size = 0xd000` is the heap size (an exact page multiple),
`heap = 0` is `freesz` (nothing free), `next = 0x8003` is the first chunk's size with its
`CUSED|PUSED` bits, and `prev == chunk` is that chunk's `->heap` back-pointer, not a self-link.
`32768 + 20464 = 53232 = 0xd000 − 16`, both allocated, which is exactly why `freesz` is 0.

So the 53248 figure was the **heap size, never a request size** — which retires the ~53 kB audio
buffer search, the `sfx_buffer.cpp:189` candidate, and the "302 ms of 16-bit stereo" reading (that
was numerology on a page multiple). `--no-sound` giving 0 events still holds, but now reads as the
audio path *driving the large-allocation path*, not writing into freed memory.

The same run still faults, now **inside the allocator** — `malloc_chunkSize` (malloc_dl.c:101) on
`far=0x4423400051392000`, a wild address. 13 bad bin entries are caught and their bins abandoned;
one gets past and faults. Two of the four fault PCs already recorded in the STK-crash row were
inside the allocator, so this looks like that row's actual mechanism.

✅ **MECHANISM FOUND (containment fix committed, NOT yet built/tested).** `free()` releases a heap
on `freesz == size - sizeof(heap_t)`, which says every byte is free but **not** that the heap is one
chunk. Two reachable paths break that invariant — `_malloc_chunkJoin()` *breaks* out on a neighbour
that fails validation (the `stopping coalesce` message), and `_malloc_chunkRemove()` can take its
abandon path mid-merge leaving a chunk free but not unlinked. The release then `munmap`s the heap
while every free chunk in it **except the first** is still threaded into a free bin. `mmap` reuses
the region for the next same-size heap, and the dangling entry reads as a sane header whose fields
are the **new** heap's — which is exactly the observed report, `heap` included (it is really
`freesz`). It is **self-feeding**: each abandon can leave another chunk unremoved. libphoenix
**`cdea6dc`** releases the heap only when it genuinely is one chunk, and prints when it is not.

⚠ **Containment, not first cause** — the invariant only breaks after some earlier problem, so the
new diagnostic is the point: if it fires, this path is real and is what turns one fault into 13.
✅ **Built and boot-tested. Result: INCONCLUSIVE, and I am not calling it a fix.** 3 STK trials with
the guard: **0 corruption events, 0 faults, 1632 / 1679 / 1704 frames** (bench complete). But the guard's own diagnostic
(`heap fully free but not one chunk`) **never fired**, which means the path it defends was not taken
— so the guard did nothing in these runs and the clean result is not attributable to it. Pre-guard
the split was 1 bad run in 2; now 1 bad in 5, against a ~40% historical rate. Not enough to claim
anything. `cdea6dc` is at least harmless (no regression, STK races 1600+ frames).

⚠ For the record: I pushed `cdea6dc` before building it, breaking my own "push once verified" rule.
It is verified now.

★ **So the next occurrence self-diagnoses instead of costing another manual decode.** libphoenix
**`3e78cbf`** computes the heap-base decode at the report site and prints `hbase?=1/0` — page-aligned,
`size` a whole number of pages, and the chunk that would sit at `heap + sizeof(heap_t)` pointing its
`->heap` back at the address. No new state; validated on the host against the exact captured bytes
(→1) and against a healthy free chunk and a page-aligned real chunk (→0).
Three **refuted** first-cause candidates (runt splits, hand-out while binned, `freesz` mis-accounting)
are recorded so they are not re-walked.
Decode, arithmetic and the ruled-out candidates:
[`docs/misc/2026-09-10-stk-audio-heap-corruption-source-sweep.md`](../misc/2026-09-10-stk-audio-heap-corruption-source-sweep.md)..

### 3e. ★★★ ROOT-CAUSED A REAL libc BUG — `strncmp` read one byte past `n`

STK faulted early, and the fault symbolised to **libphoenix `strncmp`**, not to STK:
`esr=0x92000007` (WnR clear ⇒ a **read**), `n=1`, `s1=0x0cf0dfff` — the **last byte of a mapped
page** — from `asCTokenizer::IsKeyWord()`. Both `strncmp` and `strncasecmp` looped on `*p && k < n`,
and C evaluates left to right, so the byte at index `n` is dereferenced **before** the bound is
tested. Invisible until that byte begins an unmapped page, hence "intermittent".
`strncpy`/`stpncpy`/`strncat` already ordered the bound first; **`strncasecmp` had no test at all.**
The relink did not cause this, it **exposed** it (shifted sizes moved a buffer onto a page edge).

✅ **HW-verified:** new page-edge test passes (`7 Tests 0 Failures`; `strcmp`/`memcmp` 6/0), and
**STK now reaches the race**. Negative control: the same pattern faulted on this hardware with the
old code, so the test is not vacuous. libphoenix **`f2d2789`**, tests **`a82e0e4`** + **`7c80324`**,
pushed. Manifest `manifests/2026-09-10-strncmp-over-read-fix.md`.

### 3f. The allocator defect: PROVEN shape, contained, root cause still open

**Proven.** `hbase?=1` on 24/25 then 34/34 events: the free bin holds a pointer to a **heap base**,
not a corrupted chunk. Confirmed independently by the `heap` field reading `0x4ff0` = 20464, exactly
the free remainder derived by hand (`32768 + 20464 = 53232 = 0xd000 − 16`) — so that field is
`freesz` and **the heap is live**, not released.

**Contained, and this already matters for the demo:** the latest run had **34 events, 0 faults, 1306
frames**. This defect used to end in a Data Abort inside `malloc_chunkSize()`. Validation now sits on
both bin hand-out paths — `0eab703` (large/rbtree) and **`9aaacdf`** (small/`sbins[]`).

⚠ **Four hypotheses of mine, all refuted by their own instruments.** Worth stating plainly so nobody
rebuilds them: audio write-after-free (killed by the field decode) · heap release with multiple free
chunks (`not one chunk` = 0 over 7 runs) · stale `rb_transplant` parent (`stale large-bin node` = 0
over 3 runs) · "only the rbtree lookup can produce a heap base" (`lookupbad` = 0 while 34 events
fired). The guards `cdea6dc` and `ccc0bc1` protect paths never observed to be taken — hardening, not
fixes.

★ **The lesson from the fourth:** I ruled out the small-bin path because the reported size `0xd000`
classifies as large. But **that size is read FROM the bad pointer** — a heap base reports its own
`heap->size` as a chunk size and is then printed down the large-bin branch. Size is an *output* of
the corruption, never evidence of provenance.

⏭ Open, and narrow: **how does a heap base get into `sbins[]`?** Next step is the audit on the small
path (the tree audit `1fbb6f7` never fired, consistent with the rbtree being uninvolved).
Full evidence: [`docs/misc/2026-09-10-stk-audio-heap-corruption-source-sweep.md`](../misc/2026-09-10-stk-audio-heap-corruption-source-sweep.md).
