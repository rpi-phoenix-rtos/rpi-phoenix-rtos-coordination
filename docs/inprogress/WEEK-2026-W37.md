## 3d. ★★★ NOT AUDIO — a HEAP BASE is getting into a free bin

The widened report ran on hardware and **overturned my own audio hypothesis**. The one field that
settles it is `heap = 0x0`: `malloc_chunkInit()` sets `->heap` on every chunk it makes, so an entry
with a NULL heap **is not a chunk**. Reading the same bytes as a `heap_t` header plus its first
chunk makes every field consistent — `size = 0xd000` is the heap size (an exact page multiple),
`heap = 0` is `freesz` (nothing free), `next = 0x8003` is the first chunk's size with its
`CUSED|PUSED` bits, and `prev == chunk` is that chunk's `->heap` back-pointer, not a self-link.
`32768 + 20464 = 53232 = 0xd000 − 16`, both allocated, which is exactly why `freesz` is 0.

So the 53248 figure was the **heap size, never a request size** — which retires the ~53 kB audio
buffer search, the `sfx_buffer.cpp:189` candidate, and the "302 ms of 16-bit stereo" reading (that
was numerology on a page multiple). `--no-sound` giving 0 events still holds, but now reads as the
audio path *driving the large-allocation path*, not writing into freed memory.

The same run still faults, now **inside the allocator** — `malloc_chunkSize` (malloc_dl.c:101) on
`far=0x4423400051392000`, a wild address. 13 bad bin entries are caught and their bins abandoned;
one gets past and faults. Two of the four fault PCs already recorded in the STK-crash row were
inside the allocator, so this looks like that row's actual mechanism.

⏭ **Next question, and it is narrow:** how does a heap base reach a free bin? Nothing wrote
`next`/`prev` on the entry, so it likely bypassed `_malloc_chunkAdd`'s `LIST_ADD` — pointing at the
large-bin rbtree path (`lib_treeof` subtracts 32, so a tree link at `heap_base + 32` yields exactly
the heap base, and that address is live user data) or the abandon path, over a bad split. Full
decode, arithmetic and the three candidates:
[`docs/misc/2026-09-10-stk-audio-heap-corruption-source-sweep.md`](../misc/2026-09-10-stk-audio-heap-corruption-source-sweep.md).

### 3e. ★★★ ROOT-CAUSED A REAL libc BUG — `strncmp` read one byte past `n`

Chasing the STK corruption turned up something bigger. STK faulted early this cycle, and the fault
symbolised to **libphoenix `strncmp`**, not to STK:

```
Exception #36: Data Abort (EL0)  esr=0x92000007  far=0x0cf0e000
x0=0x0cf0dfff  x2=0x1        pc -> strncmp (string/string.c:109)
                             lr -> asCTokenizer::IsKeyWord(char const*, ...)
```

`esr` WnR is clear, so it is a **read**: `n=1`, `s1` the **last byte of a mapped page**. The relink
did not *cause* this — it **exposed** it: shifting allocation sizes moved a script buffer so that it
now ends exactly at a page boundary. That is why earlier runs reached lap 1/2, and why the answer is
this fix rather than a rollback. Both
`strncmp` and `strncasecmp` looped on `*p && k < n`, and C evaluates left to right — so the byte at
index `n` is dereferenced **before** the bound is tested. Reading one byte too far is invisible until
that byte is the first of an unmapped page, which is why it presented as an *intermittent* crash.
`strncpy`/`stpncpy`/`strncat` in the same file already order the bound first; only these two were
inverted, and **`strncasecmp` had no test coverage at all.**

✅ **HW-verified:** the new page-edge test passes on the Pi (`7 Tests 0 Failures`, `strcmp`/`memcmp`
still 6/0), and **STK now reaches the race** — 8.57 / 8.10 fps in-race where before it faulted in
the tokenizer. Fix libphoenix **`f2d2789`**, test phoenix-rtos-tests **`a82e0e4`** + **`7c80324`**,
both pushed. Manifest `manifests/2026-09-10-strncmp-over-read-fix.md`.
The negative control is the STK fault itself: the same `strncmp`/`n=1`/page-edge pattern faulted on
this hardware with the old code, so the test is not passing vacuously. Verified three ways: the
built `libphoenix.a` disassembly checks `n` before every load (`cbnz x2` ahead of `ldrb [x0]`); a
host A/B with the second of two mapped pages unmapped shows the old loop faulting and the new one
returning 0; and the new loop's sign matches the system libc on 66 in-bounds cases. The new test
maps two pages and **unmaps** the second — `mprotect` is best-effort here, so a `PROT_NONE` page that
stayed readable would pass vacuously.

⚠ This is **not** yet shown to be the previously-known intermittent STK crash — two of that row's
four fault PCs were inside the allocator, so at least those are something else. But `strncmp` is
used by everything, so this is a candidate for intermittent faults well beyond STK.
