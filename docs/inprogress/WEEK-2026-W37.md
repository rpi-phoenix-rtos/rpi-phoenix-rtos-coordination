## 2c. 🔎 OPEN: an AF_UNIX liveness child `free()`s a garbage pointer (~1 in 50, not reproducible on demand)

`test-libc-unix-socket` fails about 1 iteration in 50 of `accept_connect_liveness`: the forked child
exits **70**, which is `EX_SOFTWARE` from libphoenix's allocator.

**It is NOT a double free**, despite the allocator saying so. Naming the block settled it:
`ptr=0x25e0`, `heap=0x2000`, `hsize=0x1000` — page-2 addresses, and `0x25e0` looks like an *offset*.
So the child freed a **garbage pointer**, the allocator derived a header from low memory that happened
to look self-consistent, found the in-use bit clear, and called it a double free.
`malloc_chunkValid()` passed because a fabricated header can satisfy it.

Did **not** reproduce in 350 liveness iterations (200 isolated + 150 in full-suite runs), then
recurred once when a desktop session ran first in the same boot — so the earlier "~1 in 50" was one
occurrence, not a rate. Points at libc teardown on an inherited heap, which is what this test file's
own instrumentation (a heap canary across the fork, a check for zeroed stdio globals) was built for;
neither fired.

**✅ The misdiagnosis is fixed** (libphoenix `5ece71d`): the allocator now tracks the address window
of the heaps it has actually `mmap`'d and rejects a `free()` whose heap pointer lies outside it. A
stray pointer now takes the corrupt-header path — which **leaks and reports** rather than exiting —
and the report prints the window so "never allocated here" is distinguishable from "real block,
smashed header" from the log alone. Verified for **false positives**, which is the real risk since a
wrong rejection would leak every block: `test-libc-stdlib` **92/0**, `test_malloc`'s mixed-size
stress, `test-libc-unix-socket` **27/0**, and a clean desktop exit — 0 reports, 0 faults.
⚠ Not in the flashable image above (it postdates it); the underlying stray free is still unexplained.
