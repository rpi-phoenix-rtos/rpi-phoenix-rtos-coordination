## 3. IN PROGRESS — the four bugs

**#4 — Data Abort exiting Window Maker: a KERNEL use-after-free, not an X bug.**
Reproduced with no mouse (`tests/pi-repro/wmexit.sh`) and now **fully symbolised**:

- `Exception #37: Data Abort (EL1)`, `esr=0x96000004` (level-0 translation fault, read),
  `pc=lr=0xffffffffc0008eb0`.
- Disassembly of the booted kernel (banner sha `d9048511` == `sources/phoenix-rtos-kernel`
  HEAD, so the symbols are trustworthy) puts that pc on `ldr x1,[x19,#24]` inside
  **`pmap_switch`**, where `x19` is the `pmap_t *` argument and `#24 == offsetof(pmap_t, start)`.
  `far == x19 + 0x18` and `pc == lr` because the previous instruction is `bl hal_spinlockSet`.
  Every register agrees — the attribution is not addr2line guesswork.
- **`x19 == 0x52524d2f5252434d`, i.e. the pointer VALUE is ASCII text.** The only caller
  is the scheduler (`proc/threads.c:503`, `pmap_switch(proc->pmapp)`), so the eight bytes
  at `&proc->pmapp` held text: a `process_t` was freed and its memory reused while a
  still-runnable thread pointed at it.
- **It is not plain process teardown**: `tests/pi-repro/sigterm-child.sh` (bash, background
  `sleep`, SIGTERM, exit) runs clean — so it needs the many-process, IPC-heavy X session.
- Suspect list, being worked: the **vfork window** (`process.c:1500-1560`), where the child
  adopts the parent's `mapp/imapp/pmapp` (pointers *into* the parent's `process_t`) **and
  shares its `kstack`** — while `thread_destroy()` (`threads.c:325`) does `vm_kfree(thread->kstack)`
  unconditionally.

**#1 — GPU X11 xterm resize.** Prime suspect stays our own carried pair in
`glamor_transfer.c` (RGBA upload + screen-pixmap **y-flip**): a resize repaints through
exactly those CPU upload/download paths, and the y-flip patch is the one that depends on
screen-pixmap *identity* and captures the pixmap *height* once — both of which a resize
changes. **Blocked on a repro:** `xterm -e …` launched from a script never appears (no
window, no error, no GPU work submitted) even though the desktop is up; a mouse-free
resize needs it (XTWINOPS `CSI 8;rows;cols t`). Probe cycle running.

**#2 — Quake II underwater Y-mirror.** In `ref_gl1` the *only* thing `RDF_UNDERWATER`
does is `R_SetPerspective()`'s warp (`gl1_main.c:743`): `ymax *= 1.0 - warp`, `ymin = -ymax`.
If `warp > 1` then `ymax` goes **negative** and `glFrustum` renders vertically mirrored —
which is exactly the reported symptom. So the question is what makes `warp` exceed 1
(`warp = sin(time*1.5) * 0.03 * gl1_waterwarp`). I checked libphoenix's own `sin()`
(`libm/phoenix/trig.c:77`) and its `fmod()` (`libm/phoenix/exp.c:381`): both stay in range
for Quake's argument sizes, so that is **not** it — next step is a controlled repro
(a temporary force-underwater knob), since no demo reaches water.
