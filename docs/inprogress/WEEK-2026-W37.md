## 2b. ✅ YOUR BUG #5 — mechanism CONFIRMED by measurement; same defect as bug #2

Three probes cleared every candidate path (`glamor_spans` 0 hits · `glamor_copy` 1 copy in a whole
session, neither side the screen pixmap · the readback always `y0=0 rows=1080 H=1080`, a uniform
whole-screen flip). A fourth, at the decision itself, found the cause:

**There are TWO full-screen render targets, and both are classified as "the scanout."**
```
rsc #1  1920x1080  rt=1  -> create_flags=0x2      <-- gets the framebuffer's pages
rsc #4  1920x1080  rt=1  -> create_flags=0x2      <-- gets fresh DRAM, but STILL Y_0_TOP
```
The test is `(bind & PIPE_BIND_RENDER_TARGET) && width >= 1024 && height >= 768` — a **size
heuristic standing in for scanout identity**, applied independently in `v3d_resource.c:143` and
`st_atom_framebuffer.c:137`. The winsys refuses the second claim so the pages are never shared, but
nothing stops the `Y_0_TOP` forcing applying to **both** — so the second RT renders with an inverted
viewport, and through the uniform whole-screen flip that is exactly a mirror. One such resource would
have refuted this; two confirm it. **#5 is bug #2's defect, not a separate bug.**

⚠️ **The fix I proposed last turn is withdrawn.** `PIPE_BIND_SCANOUT` is **never set** here
(`scanout_bind=0` on all nine resources), so keying off it would have compiled, changed nothing, and
cost a Pi cycle plus a re-gate to discover. `v3d_bo`'s `bool scanout` is no better — it is set from
the *request*, so both RTs carry it. Measuring before fixing is what caught this.

**Next, cheapest first:** only the winsys knows which BO really got the scanout pages, and consulting
it crosses the st↔driver boundary — so first establish **why there are two full-screen RTs at all**.
If the second is avoidable, the symptom goes with no new plumbing. ⚠️ Then owner-gated (expires the 6-app gate) — but the rebuild path is **open** again (§2b-bis).
Analysis doc §10–§11.

stripes, flat grey, MMU violations) was **one build mistake of mine**, not Mesa and not the driver.

There are two GPU X servers, differing only in how they reach V3D:
`--glamor` → `Xphoenix-glamor` (**in-process** winsys) · `--glamor-daemon` → `Xphoenix-glamor-**daemon**`

**Found on the host, no Pi cycle:** the two binaries are unstripped, so `size` + `nm` settle it —
BSS **+115 KB**, and the symbol diff names the backends (`v3d_cli_bo` 98 KB in the good one vs `W`
213 KB, the winsys global state, in mine). Built correctly on **current Mesa**: **0 faults, desktop
renders and animates** (mean 102, std 68).

**Withdrawn:** "current Mesa is not usable" (it is fine) · "the X server cannot be rebuilt" (it can)
· "glamor work is blocked" (**it is not**). The three source exonerations stand — the DDX, the Mesa

the wrong backend.

**Won't recur:** `build-xfbdev.sh` now **fails the build** if the linked backend does not match the

## 2c. ✅ ROOT-CAUSED: the X desktop's ~1 fps — presentation is a 300 ms **full-screen** timer

Not just the GL window: this caps the **whole desktop**. The DDX has a damage-driven flush and a
periodic full-frame one (`FBDEV_FLUSH_MS 300`). Instrumented the damage path — **zero calls across
two X sessions.** `fbdevShadowUpdate` never runs with glamor active, because the damage tracker is
wrapped **below** glamor (`shadowSetup` before `glamor_init` — the same layering that caused bug
#4), so GL rendering never marks the shadow damaged. That matches the readback measurement exactly:
every flush was `y0=0 rows=1080`.

So presentation is capped at **3.3 Hz** before any work, and each flush costs **8.3 MB read** out of
the screen texture plus **8.3 MB written** to `/dev/fb0`, both uncached — ~1 update/s is 300 ms plus
~700 ms of round trip. `rpi4-v3d` at 76.9 % CPU is that copying.

**Two fixes, neither cheap:** wrap damage **above** glamor (the restructuring bug #4's fix also
wanted), or **skip the round trip** — the screen pixmap's BO *does* get `V3D_CREATE_BO_SCANOUT`, and
if it is really backed by the framebuffer's pages then the readback and write are copying the
framebuffer onto itself. A cheaper third attempt (flush damaged *rows*, not the bounding box) is
**reverted**: with the damage path dead it is unreachable for the glamor desktop. Analysis doc §12.


## 2g. ✅ FIXED: "video playback rather slow" — 4.2 → **25.0 fps** (6×)

Your review said playback was slow. Measured the split before touching anything, and it was not
where it looked — the **hardware decode was never the constraint** (~3 ms/frame):

| | frame | CPU blit | fps |
|---|---|---|---|
| before | 236.3 ms | 193.8 ms (**82 %**) | 4.23 |
| after | 40.0 ms | 18.8 ms (47 %) | **25.01** |

**Root cause: both sides of the blit are uncached.** The decode buffers are
`MAP_UNCACHED|MAP_CONTIGUOUS` and `/dev/fb0` is `MAP_PHYSMEM|MAP_UNCACHED`, and the loop did 3
uncached byte *reads* per output pixel (Y,U,V) and 4 uncached byte *stores* — ~6.5 M separate bus
transactions per frame at 1280×720. Fixed by using what the SAND/COL128 layout already gives:
along a **fixed row** each 128-sample group is contiguous, so a source row is a few 128-byte
`memcpy`s into a **cached** buffer, after which the inner loop reads normal memory; plus **one
32-bit store** per pixel instead of four. Blit **10.3× faster**. The unconditional 40 ms pacing
sleep is now adaptive (sleeps only the time actually left).

Playback is now **pace-limited at the clip's native 25 fps, not compute-limited** — 47 % of a 40 ms
frame, so there is headroom for ~45 fps. Reel's video segment re-cut: **25.5 visible updates/s**,
level with the games (was 15.5). Channel order was verified against the source clip, not eyeballed
(mean R−B +10.72 captured vs +11.25 decoded on the host — an R/B swap is invisible in luma).
