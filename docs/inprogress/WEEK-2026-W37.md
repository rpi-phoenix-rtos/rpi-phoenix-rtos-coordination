## 3. IN PROGRESS — the four bugs

**#4 — Data Abort exiting Window Maker: a KERNEL use-after-free, not an X bug.**
Reproduced with no mouse (`tests/pi-repro/wmexit.sh`) and now **fully symbolised**:

- `Exception #37: Data Abort (EL1)`, `esr=0x96000004` (level-0 translation fault, read),
  `pc=lr=0xffffffffc0008eb0`.
- Disassembly of the booted kernel (banner sha `d9048511` == `sources/phoenix-rtos-kernel`
  HEAD, so the symbols are trustworthy) puts that pc on `ldr x1,[x19,#24]` inside
  **`pmap_switch`**, where `x19` is the `pmap_t *` argument and `#24 == offsetof(pmap_t, start)`.
  `far == x19 + 0x18` and `pc == lr` because the previous instruction is `bl hal_spinlockSet`.
  Every register agrees — the attribution is not addr2line guesswork.
- **`x19 == 0x52524d2f5252434d`, i.e. the pointer VALUE is ASCII text.** The only caller
  is the scheduler (`proc/threads.c:503`, `pmap_switch(proc->pmapp)`), so the eight bytes
  at `&proc->pmapp` held text: a `process_t` was freed and its memory reused while a
  still-runnable thread pointed at it.
- **It is not plain process teardown**: `tests/pi-repro/sigterm-child.sh` (bash, background
  `sleep`, SIGTERM, exit) runs clean — so it needs the many-process, IPC-heavy X session.
- Suspect list, being worked: the **vfork window** (`process.c:1500-1560`), where the child
  adopts the parent's `mapp/imapp/pmapp` (pointers *into* the parent's `process_t`) **and
  shares its `kstack`** — while `thread_destroy()` (`threads.c:325`) does `vm_kfree(thread->kstack)`
  unconditionally.

**#4 — status: root cause NARROWED, crash NOT yet fixed.** Landed in
`phoenix-rtos-kernel 20802d61` (+ a follow-up, both boot-verified): every live
`thread_t`/`process_t` now carries a magic, checked at the two wait-queue wakeup gates,
in the scheduler and in `map_pageFault`. The scheduler checks **before** unlinking,
because `LIST_REMOVE` dereferences `->next`/`->prev` and that write is how this class of
corruption turns into a second, more confusing fault. Also fixed two real lifetime bugs
found on the way: `thread_t.execkstack` was never initialised (garbage for every thread
that never vforked — and it silently disabled the kernel-stack canary, which is gated on
it being NULL), and in the vfork window an async death made `thread_destroy` free the
**parent's live kernel stack** and `process_destroy` run `vm_mapDestroy` on the
**parent's map**.

**The re-test says the crash is still there**, and that is the useful part: the second
fault landed in `map_pageFault`, not `pmap_switch`, and `current->process` was
`0xffffffff00786f62` — the ASCII `"box"`. So this is **not** a bad queue head and not the
vfork borrow: something is writing *string data* over a live `thread_t`, and the two
crashes are two victims of one wild write. The new guards exist to name the victim next
time instead of faulting three frames later. **Do not report #4 as fixed.**

**#1 — GPU X11 resize: now reproducible, and the first suspect is CLEARED.**
There was no way to drive a resize without a mouse, so I wrote one:
`tools/x11-port/xresizer` (+ `build-xresizer.sh`) resizes its own window on a timer and
paints an asymmetric pattern (red bar top, blue bar bottom, corner-to-corner diagonal) so
a mirror or a stale repaint is unmistakable on an HDMI grab.

Result over 7 resizes, **both** with no WM and under WindowMaker: **every size renders
correctly** — right way up, correct diagonal, correct borders, window correctly placed and
framed (`parent=0x200186`, root-relative 261,204). So the plain
resize-and-repaint path — including our two carried `glamor_transfer.c` patches — is
**not** the bug.

That moves the suspicion to what an *interactive* WindowMaker resize actually does and a
programmatic one does not: a **rubber-band outline drawn with an XOR GC on the root
window**, plus `XCopyArea` of window content. `GXxor` has no GPU path in glamor, so each
such op takes the CPU fallback — download the screen pixmap, do it with `fb`, upload it
again — i.e. straight through both patched functions. The probe now drives exactly that
(draw the band, undo it, then an in-window `XCopyArea`).

**Bisect result:** band-only clean, `XCopyArea`-only clean; the corrupted frame appeared
only in the combined run and only transiently. Reading that frame again, the paint order
is white → red top → blue bottom → green left → yellow right → diagonal → text, and the
artefact has red, blue and green but **no yellow and a truncated diagonal** — i.e. most
likely a **mid-repaint sample**, not corruption. So the next instrument is a rapid
continuous resize (an opaque drag) graded on the **settled** frame, and getting the
owner's real client in: `xterm -e` works both bare and under WindowMaker, so the original
xterm probe failure was the `-xrm 'xterm*allowWindowOps: true'` argument or the inner
script, which I never diagnosed.

**#2 — Quake II underwater Y-mirror: mechanism found (not yet fixed).**
The shipped renderer is **gl3/GLES3**, not gl1 (`yquake2/port.def.sh:39`), and that changes
the answer completely. In gl3, `RDF_UNDERWATER` is the *only* condition that switches the
world from direct rendering to a **render-to-FBO + post-process blit**
(`gl3_main.c:1662`), and that blit is drawn with **deliberately Y-flipped texture
coordinates** — `drawTexturedRectangleNow(x, y, w, h, 0, 1, 1, 0)`, `gl3_draw.c:390` —
because upstream assumes the window-system framebuffer is Y-flipped relative to an
ordinary FBO, which is what `gl_framebuffer::FlipY` means on a normal GL driver.

Our stack has exactly that asymmetry but *hand-rolled*: the SDL2 glue renders straight into
a scanout-backed FBO which its own comment calls **`Y_0_TOP`**
(`sdl2/glue/sdl_phoenix_glctx.c:193`), while a plain user FBO (the `ppFBO`) is bottom-origin.
So upstream's compensating flip is applied on top of ours and the underwater view comes out
upside down. The same asymmetry is why glamor needed `PHX_READBACK_FLIP_Y` and the two
`glamor_transfer.c` patches — one root cause, three workarounds. Two ways out: cancel the
flip for Phoenix in the port (one line, cheap, verifiable), or make the scanout FBO a real
`FlipY` winsys framebuffer and delete all three hand flips (the correct fix, riskier).
Ruled out on the way: libphoenix's `sin()`/`fmod()` are in range for Quake's arguments, so
the gl1 frustum-warp theory is dead.
