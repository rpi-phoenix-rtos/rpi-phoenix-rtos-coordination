## 4. ★★★ ROOT-CAUSED A REAL libc BUG — `strncmp` read one byte past `n`

STK faulted early, and the fault symbolised to **libphoenix `strncmp`**, not to STK:
`esr=0x92000007` (WnR clear ⇒ a **read**), `n=1`, `s1=0x0cf0dfff` — the **last byte of a mapped
page** — from `asCTokenizer::IsKeyWord()`. Both `strncmp` and `strncasecmp` looped on `*p && k < n`,
and C evaluates left to right, so the byte at index `n` is dereferenced **before** the bound is
tested. Invisible until that byte begins an unmapped page, hence "intermittent".
`strncpy`/`stpncpy`/`strncat` already ordered the bound first; **`strncasecmp` had no test at all.**
The relink did not cause this, it **exposed** it (shifted sizes moved a buffer onto a page edge).

✅ **HW-verified:** new page-edge test passes (`7 Tests 0 Failures`; `strcmp`/`memcmp` 6/0), and
**STK now reaches the race**. Negative control: the same pattern faulted on this hardware with the
old code, so the test is not vacuous. libphoenix **`f2d2789`**, tests **`a82e0e4`** + **`7c80324`**,
pushed. Manifest `manifests/2026-09-10-strncmp-over-read-fix.md`.

A free bin ends up holding a pointer to memory that is no longer what the bin thinks it is. Proven

reading `0x4ff0` = the exact free remainder I had derived by hand).

✅ **Contained on both hand-out paths** (`0eab703`, `9aaacdf`): a 34-event run now finishes with
**0 faults and 1306 frames** where it used to end in a Data Abort inside `malloc_chunkSize()`.
Rate since containment: **1 occurrence in 13 trials** (~8%), against ~1 in 3 before.
⚠ **Ten-plus hypotheses eliminated, four of them mine** — listed in the `STK-crash` row of
`docs/KNOWN-ISSUES.md` so they are not re-walked. Two claims I made and retracted the same day: a
shader-compilation trigger (the `Compiling shader` count is identical on clean runs, so it
discriminates nothing) and "`rm -rf` of the cache dir disables caching" (the Pi recreates it).
⚠ A fast reproducer **fails to reproduce**: `stdlib_alloc/malloc_heap_recycle_churn` (`c91eede`)
drives the exact field sizes with payload verification and passes, so the trigger needs more than
single-threaded churn.
✅ **Netboot re-proven after the image build** (loader + microkernel + `nfs;…takeover` + psh, and
`test-libc-string -g string_strncmp` 7/0 on the booted Pi).

★ **Sharpest data yet — 19/19 events in one run with `hbase?=1` AND `freed?=0`**, and `heap=0x0`
(i.e. `freesz=0`). So the address is a heap base that was **never released** and is **fully
allocated**: a *live* heap's base sitting in a free bin. That retires the last surviving form of my
recycling theory.
⏳ One alternative left, now instrumented: `hbase?` is a *value* test, so a live block whose payload
begins with a size-like word and a **self-pointer** (an ordinary embedded list head) would satisfy it
too — and "heap base in a bin" vs "live block with a look-alike payload in a bin" need different
fixes. libphoenix **`b6b7f29`** adds a 16-slot ring of the bases actually `mmap`'d and prints
**`lheap?=`**; a hit is proof rather than inference. Slots clear on release, or the field would call
a released heap live and contradict `freed?=`.
⚠ **12-trial hunt caught 3 events — and exposed a flaw in my own instrument.** All three read
`hbase?=1`, `freed?=0`, **`lheap?=0`**. But the live ring held only **16** slots, and STK gives almost
every large allocation its own heap, so the base is evicted long before the bin entry is rejected:
`lheap?=0` there means *"evicted"*, not *"not a heap"*, and the two readings are indistinguishable.
Fixed in libphoenix **(ring → 256 slots + an `lovfl` overflow counter that says outright when the
verdict cannot be trusted)**. Also a **new event shape**: `size=0x81000` (a 129-page heap), not the
0xd000 stride seen before.
★ **A 137030-line `freed?=` flood in one trial was a HOST CAPTURE ARTIFACT, not a target bug** — all
of it sits *before* the boot banner (line 2 → 264727, banner at 264885), i.e. the serial tool
re-reading a stale buffer while the Pi was off. It polluted the first tally I ran. This is the third
time this artifact has been mistaken for a target fault; check the flood against the banner position.
⚠ Earlier 4-trial hunt: 0 events (~32% by chance at the ~1-in-4 rate), so
`lheap?=` is armed but unexercised. It costs a few stores per heap allocation, so it stays in
permanently and the next occurrence in any app reports it.

⚠ **Second hunt (10 trials, 256-slot ring): 0 events** — so `lheap?=` is *still* unexercised and the
