## 2e. ✅ A libc bug found by chasing the ntpclient crash — `getaddrinfo` leaked and lied

`getaddrinfo()` did `*res = msg.o.data = realloc(msg.o.data, bufsz);`. On a failing `realloc` that
**leaked** the original block *and* returned **0 with `*res == NULL`** — which every caller
dereferences immediately (ntpclient does `res->ai_family` on the next line). libphoenix **`75bf050`**
keeps the larger buffer instead, since the shrink is an optimisation, not a requirement.

★ **It had NO test coverage** — no staged suite referenced `getaddrinfo` at all, which is how a
success-with-NULL-result survived. phoenix-rtos-tests **`fc3dd0f`** adds it: **HW 2/2 PASS, 0
exceptions**. DNS-free by construction (`AI_NUMERICHOST`/`AI_PASSIVE`) so it cannot fail because a
nameserver is unreachable, checks that `AI_NUMERICHOST` *rejects* a non-numeric name, and repeats the
lookup 32× so a leak shows up rather than passing once by luck.

⚠ **Not claimed as the ntpclient fix.** That fault is a 720-byte `memset` **write** through NULL;
this path yields a NULL **read**. Independent defect, same code path — the ntpclient row keeps its
own next step.

## 2f. ✅ ROOT-CAUSED a libc startup crash — and it points at the loader

A repeatability gate flagged Quake II with **2070 exceptions**. Quake II was innocent: `/bin/ntpclient`
and `/bin/psh` are **byte-identical** (psh under an applet name), so the unstripped `prog/psh`
symbolises it — PC is `memset`, **`lr` is `_atexit_init`**, and the call is
`memset(atexit_common.head, 0, 784)` with **`head == NULL`**. libc was dying **before `main()`** with
no diagnostic at all.

**Fixed** (libphoenix **`160e916`**): the first node is a NAMED static object and `_atexit_init()`
recovers instead of faulting. Verified in the generated code (`cbz x0` now guards the `bl memset`
that sits at the crash's exact `lr`) and on hardware (93/0, 2/0, 0 exceptions).

⚠ **The interesting part is what remains.** The ELF is *correct*: `.data` holds the right pointer
(`0x4373e0` = `atexit_firstNode`). So a runtime NULL means **`.data` did not reach the process
intact** — a **load-time** failure. `/bin/psh` is demand-paged from the NFS root, and this codebase
has already fixed one short-read defect on that path (`vm/object.c` `f145658f`, for **text**). ★ This
would affect **any** statically initialised pointer, so it is worth more than the one crash it
caused — recorded as `atexit-null-head` in `docs/KNOWN-ISSUES.md`.

## 4. ★★★ ROOT-CAUSED A REAL libc BUG — `strncmp` read one byte past `n`

STK faulted early, and the fault symbolised to **libphoenix `strncmp`**, not to STK:
`esr=0x92000007` (WnR clear ⇒ a **read**), `n=1`, `s1=0x0cf0dfff` — the **last byte of a mapped
page** — from `asCTokenizer::IsKeyWord()`. Both `strncmp` and `strncasecmp` looped on `*p && k < n`,
and C evaluates left to right, so the byte at index `n` is dereferenced **before** the bound is
tested. Invisible until that byte begins an unmapped page, hence "intermittent".
`strncpy`/`stpncpy`/`strncat` already ordered the bound first; **`strncasecmp` had no test at all.**
The relink did not cause this, it **exposed** it (shifted sizes moved a buffer onto a page edge).

✅ **HW-verified:** new page-edge test passes (`7 Tests 0 Failures`; `strcmp`/`memcmp` 6/0), and
**STK now reaches the race**. Negative control: the same pattern faulted on this hardware with the
old code, so the test is not vacuous. libphoenix **`f2d2789`**, tests **`a82e0e4`** + **`7c80324`**,
pushed. Manifest `manifests/2026-09-10-strncmp-over-read-fix.md`.
