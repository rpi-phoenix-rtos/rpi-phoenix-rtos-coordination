`std::thread::hardware_concurrency()`, which the libstdc++ fix took from 0 → 4, so the pool went

baseline. Patch reverted rather than shipped; a no-op change is worse than none.

granular before the fix. But every caller is `ge_vulkan_*`, and this port runs the **GLES/SP** path —
inert here.

our own rule the right instrument is a **flip counter over a fixed window**, not the HUD — that is
the next step if this 2 fps is judged worth more time.

## 2c. 🔎 STILL OPEN: AF_UNIX liveness double free — hypothesis narrowed again, no reproduction

The third child of `accept_connect_liveness` occasionally exits **70** (`EX_SOFTWARE`) from
libphoenix's allocator reporting a double free. Four occurrences, all on the same assert, none
reproduced on demand.

**Established so far.** It is always the **third** child — the only one in the suite that calls
`unlink()`, and `unlink()` is the only code any child runs that calls `free()` at all. `exit()` in
this binary frees nothing. So the "libc teardown" theory is dead and it is on the **path-resolution**
route: the two `malloc(PATH_MAX)` blocks in `resolve_path` (which land in a **large** bin).

**This turn — an informative negative.** libphoenix already ships `malloc_test()`, which walks every
small bin and every large-bin rbtree and asserts `!(chunk->size & CHUNK_CUSED)` — precisely the
precondition for "malloc handed the same chunk out twice, so two correct `free()`s free one block".
Wired it into the test at the two places that attribute rather than merely cover: the **parent** once
per iteration (where such corruption would originate) and the **child** immediately before its
`unlink()`. Result over **6 runs ≈ 300 third-children: 0 violations, 27/0 every run, no
reproduction.**

So the bins are **not** left persistently corrupt, which is what that variant of the hypothesis
required — it is now disfavoured. What remains: a transient header smash (the overrun candidate), or
a duplicate hand-out consumed entirely between two checkpoints. The latter is already covered
everywhere by the `_malloc_allocFrom` CHUNK_CUSED check shipped earlier, which fires on **every**
allocation path.

⚠ Not fixed, and not claimed to be. Two fixes this week removed *candidates* rather than the cause:
the large-bin abandon path (`79716ad`, a regression of mine) and the unclamped readlink count
(`50eab64`, §2e). The next occurrence is now self-diagnosing — and capture the **whole** five-line
report (`ptr/size/heap/hsize/hfree`); `size` identifies the block class and was the field thrown away
last time.
