★★★ **STK's remaining crash is ROOT-CAUSED, in STK's own code, and it is NOT the allocator bug.**
It faults with **no allocator report at all**, in `DriveGraph::getAngleToNext`, on
`far=0x800000010d009d78` — bit 63 set, which a valid aarch64 userspace pointer never has. The chain,
read from source:

`Graph::UNKNOWN_SECTOR = -1` → `AIBaseLapController::steerToAngle(**const unsigned int** sector, …)`
converts it to `0xFFFFFFFF` at the call boundary → `DriveGraph::getNode(unsigned)`, whose only bounds
check is **`assert()`, compiled out under `NDEBUG`** → `m_all_nodes[0xFFFFFFFF]` reads ~32 GiB past
the vector → `dynamic_cast` dereferences the garbage's vptr → the Data Abort.

That explains both oddities: it needs a kart **off the drive graph** (rescue, off-track, respawn) to
produce a negative sector, hence the intermittency; and it is latent upstream because with asserts
on it aborts loudly, while on a desktop the wild read usually lands on *mapped* memory and merely
produces nonsense steering. It is fatal here only when that address is unmapped.

✅ **Prediction tested and confirmed: `--numkarts=1` removes the AI controllers, and the crash goes
with them — 0 crashes in 7 trials** (~1580 frames each, very consistent), against 1 in 3 at
`--numkarts=4`. Prediction and observation agree, which is the first time today a mechanism I
proposed survived its own test.

⏸ **YOUR CALL — two options, both cheap:** (a) drop the showcase kart count, trading four racing
karts for stability with no code change; or (b) take a one-line **port patch** guarding the
conversion (reject `UNKNOWN_SECTOR` / out-of-range before it reaches the graph) — STK is GPL-3, so

## 4. ★★★ ROOT-CAUSED A REAL libc BUG — `strncmp` read one byte past `n`

STK faulted early, and the fault symbolised to **libphoenix `strncmp`**, not to STK:
`esr=0x92000007` (WnR clear ⇒ a **read**), `n=1`, `s1=0x0cf0dfff` — the **last byte of a mapped
page** — from `asCTokenizer::IsKeyWord()`. Both `strncmp` and `strncasecmp` looped on `*p && k < n`,
and C evaluates left to right, so the byte at index `n` is dereferenced **before** the bound is
tested. Invisible until that byte begins an unmapped page, hence "intermittent".
`strncpy`/`stpncpy`/`strncat` already ordered the bound first; **`strncasecmp` had no test at all.**
The relink did not cause this, it **exposed** it (shifted sizes moved a buffer onto a page edge).

✅ **HW-verified:** new page-edge test passes (`7 Tests 0 Failures`; `strcmp`/`memcmp` 6/0), and
**STK now reaches the race**. Negative control: the same pattern faulted on this hardware with the
old code, so the test is not vacuous. libphoenix **`f2d2789`**, tests **`a82e0e4`** + **`7c80324`**,
pushed. Manifest `manifests/2026-09-10-strncmp-over-read-fix.md`.
