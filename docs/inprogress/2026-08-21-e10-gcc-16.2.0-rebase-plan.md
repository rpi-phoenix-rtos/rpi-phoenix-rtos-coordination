# E10 — gcc 14.2.0 → 16.2.0 toolchain rebase: assessment + plan (2026-08-21)

Owner-greenlit "big achievement" goal. Current Phoenix cross-toolchain =
**gcc-14.2.0 + binutils-2.43** (`sources/phoenix-rtos-build/toolchain/build-toolchain.sh`
`GCC=gcc-14.2.0`, line 66), with 11 gcc + 4 binutils Phoenix patches.

## Feasibility: TRACTABLE (patch-port) but the revalidation is the real cost

- **gcc 16.2.0 EXISTS** on the GNU ftp (16.1.0 + 16.2.0 both present). binutils
  stays 2.43 (unchanged) → its 4 patches are unaffected.
- **Patch-port scope (gcc-14.2.0-* → gcc-16.2.0-*):** most patches are small and
  touch **target-definition files** that are additive + stable across gcc majors:
  - `11-aarch64-phoenix` (57L: `gcc/config.gcc` + `libgcc/config.host`) — the key
    one for RPi4; small, stable files.
  - `09-fix-libc-spec` (15L: `gcc/config/phoenix.h`) — small, phoenix OS header.
  - `04-arm-pic_crtstuff` (30L: `libgcc/config.host` + arm t-phoenix) — config.host
    is shared; arm t-fragment.
  - The arm/i386/riscv64/sparc patches (01/02/03/06/07/08/10) are for **other
    Phoenix targets** — needed only if building those; irrelevant to the aarch64
    RPi4 toolchain.
  - **`05-libstdcpp` (265L: `libstdc++-v3/configure`) = the RISK.** `configure` is
    auto-generated and regenerates between majors, so this patch will likely
    reject and need re-derivation (find the phoenix host cases in gcc-16.2.0's
    configure + re-add). Alternatively re-derive from `configure.ac` if the
    upstream generator is available.
- **Build is SAFE to attempt:** `build-toolchain.sh <target> <install-path>` takes
  the install prefix as `$2` → build to a **separate prefix** (e.g.
  `.toolchain-gcc16`), never touching the working `.toolchain`. Guards: aborts if
  `${TARGET}-gcc` is in PATH or CC/CFLAGS/... are set (run with a clean env).

## The real cost / risk (why this is multi-week + partly attended)

The patch-port + toolchain build is bounded. The EXPENSIVE + RISKY part is
**rebuilding all of Phoenix (kernel + libphoenix + ports) with gcc 16.2.0 and
revalidating** — a new gcc major routinely surfaces new `-Werror` warnings,
stricter UB handling, and codegen differences that can break subtle things across
the whole system. That revalidation needs owner judgment on breakages and is best
done attended (or at least owner-aware). **Do NOT swap gcc-16 into `.toolchain`
unattended** — everything depends on the working gcc-14.2.0.

## Plan (staged)

- **E10-M0 (unattended, SAFE — in progress):** port the aarch64-relevant patches
  (11/09/04 + the shared config.host bits; defer/skip the other-arch ones) to
  gcc-16.2.0, build a gcc-16.2.0 aarch64-phoenix cross-toolchain to a **separate
  prefix**, and compile-test a hello-world. Success = the toolchain builds + emits
  a working aarch64-phoenix binary. Resolve `05-libstdcpp` reject (or build
  `--without-libstdcxx`-style C-only first if C++ is not needed for the smoke).
- **E10-M1 (attended/owner-aware):** rebuild Phoenix (kernel/libphoenix/ports)
  with the gcc-16 toolchain, triage every new warning/error/codegen diff, HW-boot,
  full regression. Only then swap `.toolchain`.

## Recommendation

The rebase is worth doing (owner-greenlit) and M0 is safely attemptable now. M1
(the system revalidation) should be attended given the breakage surface. This turn
kicks off M0 (build the gcc-16.2.0 toolchain to a separate prefix).
