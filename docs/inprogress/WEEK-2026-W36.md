## 3. IN PROGRESS

**SD card driver — "full speed + correctness"** (the standing `/loop` goal; card is in the Pi)
- ✅ **Rig DONE and reproducible from a clean build, no changes needed**: the `nfsroot` variant already starts a probe-only `bcm2711-emmc` (upstream, gated `!= sd`), so the card appears as `/dev/mmcblk0` while `/` stays on NFS; `sdtest` is served from the NFS root. No card swaps, no host reader, no boot-config edits.
- ✅ **Repeatable numbers** at `UHS-I DDR50 1.8V`: **write 18.3–19.2 MB/s (PIO), read 30.3–33.1 MB/s**.
- ✅ **Correctness proven CACHE-COLD**: 16 MiB pattern written in one boot, power-cycled, read back byte-identical in the next (`sdtest write` / `sdtest verify`). PIO writes are sound on the physical card.
- ✅ Two earlier mysteries closed: my boot brick was a **duplicate** of the pre-existing emmc line (duplicate plo file-alias), and the "DDR50→High-Speed downgrade" was just my own redundant *second* driver instance — **not** a driver bug. Nothing to chase there.
- ⚠️ Remaining lever = the SDMA-write gate (`sdcard.c:1625`), left **OFF**. A gate-ON boot previously left a file on the card unreadable; the write path is structurally fine (bounce copy-in present), so it looks like the documented controller quirk → D3.

**Upstream tracking** — ✅ automated: `scripts/upstream-status.sh` (read-only digest: behind/ahead + new upstream subjects per repo) + a **weekly cron (Mondays 07:12)** that digests, merges the safe set, rebuilds, boot-tests, pushes only what passed, and logs anything it declined. `git-pull-upstream-all.sh` does the merge. Caveat: crons are session-scoped, so this lives as long as the Claude session.

**WiFi (E7)** — data-plane protocol-complete (DHCP lease). ✅ **F2 RX read fixed in BOTH codebases** — two-phase (12-byte SDPCM header, then exactly the remainder, per `brcmf_sdio_readframes`), buffer 512→2048 B, over-long frames refused rather than truncated. HW-verified: (a) probe — join + OFFER + REQUEST/ACK still bind 10.43.0.89; (b) resident driver (devices `be7c62a`) — full bring-up → `/dev/wifi`, and `wifi scan` returns real APs, which exercises the large escan event frames. ✅ **Daemon does WPA2 join + full DHCP by itself — HW-PROVEN** (devices `b242f55`): `wifi netup <ssid> <psk>` → `join setssid=0 psksup=6 link=1` + `dhcp offer=1 ack=1 bound_ip=10.43.0.89` → `RESULT BOUND`: the resident driver gained the WPA2 join + the data path (TX + ch2 RX + the two-phase DHCP flow), exposed as `wifi netup <ssid> <psk>` → reports the bound IP. +735 lines, reuses every existing helper (no duplication), builds with zero warnings; two deliberate improvements over the probe: DHCP is gated on join success, and all result globals reset per call (a stale `serverid` would otherwise poison the next REQUEST's opt54). ⚠️ Operational caveats: `netup` blocks the `/dev/wifi` write **synchronously up to ~90 s**; the only proven ordering is **netup as the first command after daemon start** (netup-after-scan and a second netup on already-associated firmware are untested — no disassoc is issued); DHCP xid is a fixed `0x12345678` (matters when reading dnsmasq logs; two concurrent netups would collide).
