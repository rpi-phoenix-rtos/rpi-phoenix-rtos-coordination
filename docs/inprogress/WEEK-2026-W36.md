## 4. PROGRESS THIS WEEK (terse; detail in `docs/done/`)

- **★★★★★ ROOT CAUSE OF THE GPU "WEDGE": WE FEED IT A CONTROL LIST THAT HAS BEEN OVERWRITTEN WITH RGBA PIXEL DATA. It is not a marginal-hardware stall.** Found by decoding all 72 recorded `RCLBYTES` dumps offline (pure Python against existing logs — no Pi, no build) and correlating the decode against where CT1 actually stopped:
  | list state | where CT1 parked | count |
  |---|---|---|
  | **all garbage** — pixels from byte 0 | **0x0 / 0x1** | 40 |
  | **partial** — valid list, then pixels from offset **66** | **0x43 / 0x70** | 6 |
  | **valid list** — walks cleanly to `END_OF_RENDERING` | 0x1000+, or outside the list | 23 |
  **Every job where the GPU parked *inside* its list had the list corrupted at exactly that point; every job with an intact list parked *outside* it.** The famous park at `0x43` is not "Mesa's GFXH-1742 dummy tile-store misbehaving" — in a clean list offset 66 is `END_OF_LOADS` and 67 (=`0x43`) is the store, and in the corrupt ones offset 66 is **pixel data**. The GPU is refusing garbage, correctly. The "HW-marginal depth-pipeline drain stall" story in the driver comments is wrong for this whole class, which also matches the standing rule that these bugs are ours, not the silicon's.
  - **The partial cases are the proof it is an OVERWRITE, not a mis-built list.** The first ~66 bytes decode as a correct RCL (`79 79 79 7e 7b 7a 7c 1a 1d 1b 7c …`) and the tail is unmistakably RGBA8 — `0xff` in every 4th byte (alpha) in 4 of the 6. Mesa built a good list into that buffer and something wrote an image over its tail.
  - **Structure confirmed while doing it:** `rcl_len = 92 + 3 × n_supertiles` holds for **every** intact list (95, 98, 101, 107, 122 → n = 1, 2, 3, 5, 10), and the walker accepts 23/23 intact lists and rejects 46/46 corrupt ones. So the classifier the CPU-copy rescue needs is validated **before** any C was written — and it caught that the plan's "accept all 0x79 openers" assumption was wrong (6 of them open with `0x79` and are still corrupt).
  - **The MMU faults corroborate it independently.** Across the logs the fault addresses are **wild** — `0x702c0000`, `0xfff7e000`, `0xe1618000`, `0xc2df6000`, `0x6bc3a000` — far outside the GPU's ~80–180 MB VA window, plus **260** faults at `0x00000000`, all reported as "NO live BO covers it". That is precisely what a GPU does when it reads pixel bytes as CLE packets and branches to whatever the next four bytes happen to be. And the corrupt tails are recognisable content, not noise: `67 4f 30`, `d6 c1 8d`, `ea d0 9a`, `f7 e4 ae` are Quake browns/tans. So a **live control-list BO is holding real texture data**, and the open question is only how — physical-page double-allocation, a stale GPU page-table entry after a BO close, or a write through a second mapping.
  - **A tempting cache explanation, checked and REJECTED before it became a wrong fix.** A 64-byte-granular partial corruption is the classic signature of dirty CPU cache lines never reaching DRAM, and the winsys *does* have a cacheable-BO path (flags bit 0 drops `MAP_UNCACHED`, `:686-692`) whose create-time `memset(0)` would then also stay in cache — the GPU would read the page's previous contents, i.e. exactly the texels we see. It even fits the driver's own note that garbage in a CL makes "CT1 branch to a wild address … and wedge". **But V3DV never sets that flag** — a search of `external/mesa/src/broadcom/vulkan` finds no `CREATE_BO_CACHEABLE` user; only gallium GL has the path, and *its* comments record that making a BO CPU-cacheable "hangs the GPU/render after the first cacheable readback", so it was disabled rather than root-caused. vkQuake's control-list BOs are therefore **uncached**, and this mechanism cannot be the cause for them. Worth keeping in view anyway: that disabled-and-never-explained GL hang has the same shape, and `struct pbo` still records no `cacheable` flag at all, so the winsys cannot tell.
  - **This reorders the work.** The CPU-copy rescue would paper over the symptom for at most a third of cases. The real bug is *whatever writes texels into a live control-list BO* — and `DRM_V3D_MMAP_BO` handing Mesa `b->cpu` itself makes BO recycling the first place to look. The already-committed entry-time check (devices `c73f5f0`) now answers the decisive question: corrupt **at submit** ⇒ a BO-lifetime/aliasing bug above the winsys; intact at submit ⇒ something overwrites it while the job runs.

- **★★★ THE DROPPED-JOB CL IS NOT MALFORMED — our own driver comment was wrong, and decoding it found a SECOND defect** ([full decode + patch plan](../misc/2026-09-03-v3d-dropped-metacopy-fix-plan.md); comment corrected in devices `bb13969`).
  - The driver concluded, from the wedge being deterministic, that "the CL itself is malformed". **It is not.** The 98-byte RCL was decoded packet by packet against Mesa's `v3dvx_meta_common.c` and matches upstream **byte for byte**.
