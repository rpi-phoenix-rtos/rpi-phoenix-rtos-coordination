  - **Leading mechanism, and it is a DRM semantics bug of ours:** `DRM_V3D_MMAP_BO` hands Mesa **`b->cpu` itself**, and then `ioc_close_bo` **`munmap`s that pointer**. In real DRM, closing a GEM handle does *not* invalidate a CPU mapping the process already holds — so a Mesa bufmgr that still has the BO mapped (its cache keeps mappings alive) is left holding a dangling pointer, and the **next** BO's `mmap` is handed the same address back. Mesa's image writes then land inside a freshly created BO — which is exactly a control list full of texels. Compounding it, `b->handle = slot + 1` means **handles are recycled** too, so a stale handle resolves to a live, different BO instead of failing.

That last point cuts both ways and is worth stating: the mutex **cannot** protect against this bug at all, because Mesa writes control-list bytes by **CPU into the mapping**, with no ioctl to serialize.

- **★★★ A SECOND REAL DEFECT FOUND WHILE HUNTING THE CORRUPTION: closing a BO left its GPU page-table entries live** (devices `6c1e321`). `ioc_close_bo` freed the VA range and `munmap`'d the pages but never invalidated `W.pt` for that range. `munmap` returns those physical pages to the Phoenix kernel, which hands them to the next allocation — so a stale PTE points the GPU at memory that now belongs to something else, and it reads or writes it **silently**. Two concrete ways it bites in this very file: `va_free()` returns N pages and a later **smaller** BO takes the same VA, whose mapping loop rewrites only the pages it uses so the tail keeps pointing at recycled memory; and anything still holding the old VA (a pointer left inside a reused control list) resolves through a translation that is no longer ours. Clearing the PTEs turns both into a **reported** MMU fault (`MMU_CTL_PTI_ABORT` is already on) instead of quiet foreign data — which is exactly the class of path that can leave a live GPU address on someone else's memory, i.e. how texels end up where a control list should be. Safe against free-while-referenced because submits here are synchronous, and no TLB clear is needed since every submit path already calls `mmu_flush_tlb()`.
