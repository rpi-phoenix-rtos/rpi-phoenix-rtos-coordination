0. **AF_UNIX: the remaining bug is a ZEROED MEMORY REGION in the forked child — instrumented, waiting for a hit.** ⚠️ **Correction to yesterday's claim: the id fix is NOT the cause of the cross-delivery.** The mismatch reproduced with it in place (`DATA-MISMATCH ... data[]=INTACT`, `recv bytes appear nowhere in data[]`), and the logic never fit: `unix_transfer` uses **`socketpair`**, so no pathname is ever resolved and stale-name/id-reuse cannot apply. The id fix stays (a real hazard, ECONNREFUSED semantics now pinned by tests) but it is not this bug. Also: the earlier "read-overrun eliminated" came from a **passing** run, so it eliminated nothing. **What the crashes now say, precisely:** two different child faults have the SAME shape — a pointer that must be valid reads NULL. `fwrite` -> `mutexLock(stream->lock)` at `far=0x30` (a NULL `FILE *`; stdio globals are heap pointers in `.data` from `_file_init`) and `_malloc_chunkRemove` -> `lib_listRemove` at `far=0x10` (a NULL free-list link, `esr` = level-3 **write** fault). One region of the child's memory going to zeros explains both; a COW fault installing a fresh zero page instead of a copy is the obvious producer, and this path has had a COW/PROT_USER bug before. **Instrumented (tests `83eda31`, pushed):** the child now receives into a **stack** buffer (private by construction — separates "socket delivered foreign bytes" from "the page we read back is not the page the kernel wrote"), and a 64 KiB canary filled in the PARENT is verified in the child (inherited COW, so a zeroing fault shows as a run of zeros, reported with offset, offset-within-page, run length and whether it is zeros). Both reports use raw `write(2)` + `_exit` because stdio and malloc are the suspects. **Rates so far, honestly:** with `.bss` recv 1 mismatch in 12 runs; with stack recv **0 mismatches in 9** (too few to conclude) and 1 crash-family run. **Next: keep running trials until a canary fires, then read the offset/run to confirm or kill the zero-page theory.**
