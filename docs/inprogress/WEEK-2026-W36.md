## 2. PLAN FOR THE NEXT DAYS

1. **WiFi performance — SOLVED for now: RX 0.14 → 3.0 MB/s, TX → 3.3 MB/s.** The firmware aggregates inbound frames into SDPCM channel-3 superframes and we dropped every one (~18% of all RX); it **cannot be disabled** (`bus:rxglom=0` accepted and ignored), so it is now **de-aggregated**. The key was dumping a superframe and decoding it instead of guessing the stride: subframes sit in the **descriptor's slots measured from the start of the superframe** (slot 0 also holds the superframe's 12-byte header — headers at 12/96/192/288, gaps 84/96/96, slots summing to exactly the superframe length). Measured, 3 runs each: **TX 0.22–0.66 → 3.27 MB/s, RX 0.13–0.29 → 3.00 MB/s**, and the wild variance is gone — it was frame loss driving retransmit storms, not the radio. 740 superframes → 3595 subframes, `bad=0`, `rx_err=0`. devices `4e8a7e9`. Next (optional): per-frame overhead is the remaining ceiling; wired genet is ~30/20 for scale.
2. **V3D driver → `phoenix-rtos-devices`** (D2) — investigated and staged; **Stage 0 done**, Stage 1 needs your read of D2 (see D9). Key finding: *"move it all" is not achievable* — the three archives are ~99% compiled Mesa and their build needs meson + `ninja` codegen + a host `compile_commands.json` + the 1.2 GB `external/mesa` clone, none of which a devices framework component can do. What we own is ~3.7k lines of glue, and **half the driver already lives in `devices/gpu/rpi4-v3d/`** (the GPU server + client lib + the same UAPI headers `tools/` duplicates). Achievable scope = move the glue + build scripts on the `wifi/rpi4-wifi` model (source in devices, standalone script, gitignored outputs), Mesa and `tools/.gpu-libs/` stay put. Plan + hazards: `docs/misc/2026-09-02-v3d-migration-plan.md`.
3. **NFS-over-WiFi** (optional, closes the perf ask fully) — TCP numbers are in (3.3 TX / 3.0 RX); an NFS workload over `wl2` would need a second mount alongside the NFS root, so it is deliberately deferred rather than risk the netboot rig.
