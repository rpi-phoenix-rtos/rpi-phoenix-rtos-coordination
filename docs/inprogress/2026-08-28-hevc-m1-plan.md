# HEVC M1 — hardware H.265 decode bring-up plan (BCM2711 rpivid)

**Owner-approved thrust** (2026-08-28: "pursue the full HEVC/rpivid port"). This is
milestone **M1** of the staged HEVC plan (see `project_ffmpeg_hw_decode_scope` memory):

> M0 bring-up smoke ✅ → **M1 IRQ SPI-98 + contiguous/uncached bitstream+DPB allocators**
> → M2 port the `hevc_d_h265.c` register decode core → M3 ffmpeg HEVC-parser client glue
> → M4 SAND→linear de-tile + HDMI + CPU-vs-SW-baseline measure.

## What M0 already proved (`tools/hevc-probe/`)

The rpivid/hevc_dec block is reachable from Phoenix over plain uncached MMIO, **no
VCHIQ**: enable the HEVC clock via the VideoCore mailbox (firmware clk id 11), map
the HEVC block @`0xfeb00000` (0x10000) + ARGON INTC @`0xfeb10000` (0x1000), read the
version register (offset 60) = **0x202** (liveness oracle), enable the ARGON INTC
(`ARG_IC_ICTRL` offset 0, `ACTIVE1_EN_SET` BIT(2) | `ACTIVE2_EN_SET` BIT(6)).

## M1 objective

Stand up the two decode prerequisites, each independently HW-verifiable **before** the
dense per-slice register programming (M2):

1. **Contiguous/uncached DMA buffer allocator** for the decode working set (bitstream
   input + the decoder's working/aux buffers + DPB/reference frames + output NV12).
2. **IRQ delivery** — the HEVC "decode done / error" interrupt (GIC **SPI 98**) routed
   to a Phoenix handler, acked via the ARGON INTC status register.

## Confirmed Phoenix primitives (reuse, do not reinvent)

- **Contiguous uncached DMA memory** (the exact idiom the V3D port uses, proven on this
  HW — `tools/v3d-driver-port/v3d_phoenix_winsys.c:302`, `v3d_phoenix_power.c:77`):
  ```c
  void *cpu = mmap(NULL, size, PROT_READ|PROT_WRITE,
                   MAP_UNCACHED|MAP_CONTIGUOUS|MAP_ANONYMOUS, -1, 0);
  addr_t pa = va2pa(cpu);   /* Phoenix syscall, <sys/mman.h> — 32-bit ARM PA on 4GB Pi4 */
  memset(cpu, 0, size);     /* MAP_CONTIGUOUS returns NON-zeroed DRAM (no __GFP_ZERO) */
  ```
  The rpivid DMA engine is 36-bit; on the 4 GB Pi4 every `va2pa` result is < 4 GB, so the
  physical address programs directly into the block's buffer-base registers (confirm the
  bus-address convention — plain PA vs `0xc……` alias — from the Linux driver in M1 test).
- **Mailbox clock**: `libvcmbox` (`sources/phoenix-rtos-devices/misc/rpi4-vcmbox/`), linked
  the same way `tools/hevc-probe/build-hevc-probe.sh` does.
- **MMIO map**: `mmap(MAP_DEVICE|MAP_UNCACHED|MAP_PHYSMEM|MAP_ANONYMOUS, -1, pa)`.
- **IRQ**: Phoenix `interrupt()`/`threadJoin` SPI registration (pattern to confirm from an
  existing Pi4 device driver that takes a GIC SPI, e.g. genet/emmc2).

## M1 deliverables (this + next turns)

- `tools/hevc-decode/` (new): an M1 harness that (a) enables the clock + maps the blocks
  (M0), (b) allocates the full contiguous DMA working set with a small `dma_alloc()` helper
  returning `{cpu, pa, size}`, (c) registers the SPI-98 handler + arms the ARGON INTC,
  (d) prints the allocation table (cpu/pa/size) + waits briefly to confirm no spurious IRQ.
  This is the scaffold M2 hangs the `hevc_d_h265.c`-derived register programming onto.
- A register-map header (`hevc_regs.h`) with the decode-path offsets/bitmasks the M2 core
  needs — populated from the Linux `hevc_d_hw.h` analysis (subagent spec, in progress).

## Risks / unknowns (resolve during M1 HW test)

1. **Bus-address convention** for buffer-base registers (plain PA vs `0xc0000000` alias).
2. **DMA reach** — confirm `va2pa` buffers land < 4 GB and the block accepts them; the
   36-bit engine wants specific alignment (from the Linux driver's `dma_alloc` alignments).
3. **IRQ actually fires only on a decode** — SPI-98 can't be exercised in isolation without
   M2's decode kick, so M1's IRQ test is "registers cleanly + no spurious", full validation
   lands with the first M2 decode.

## Constraints

- Additive `tools/` work only — **must not touch or destabilize the Sunday-demo path**
  (games + X desktop on the fresh gcc-16 netboot rootfs).
- No VCHIQ, no firmware decode blob (fixed-function block).
- Output is Broadcom SAND/column-128 tiled NV12 → CPU de-tile deferred to M4.
