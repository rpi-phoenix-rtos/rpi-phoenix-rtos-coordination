## C3

**Issue:** **Two libc globals read back zero, killing the process at `main`.** `stderr` and psh's applet list are both unset, so `fprintf` dereferences a NULL `FILE*` (`far=0x30`). Both live in one 4 KiB `.bss` page. A source review gave a clean negative on every kernel mapping path, so "those writes definitely execute" is the assumption the next occurrence has to test.

**Last measured:** **2 sightings (2026-09-07, 2026-09-15), none since.** Impact limited to `ntpclient`, which only sets the clock. The label added to make a recurrence self-explaining (`applet list is empty`) has **never fired** in the whole archive. ✔ **2026-09-24 — two constraints added, and one suspect cleared.** (a) **The two globals come from DIFFERENT mechanisms at different times**: `stderr` is assigned in `stdio/file.c:1565` reached from `_libc_init()`, while psh's applet list is filled by an `__attribute__((constructor))` (`pshapp/env.c`) run later from `_init_array()` — and `crt0-common.c:_startc` runs `_libc_init()` *then* `_init_array()` *then* `main()`. So this is **not** "constructors didn't run": two independent writes, both lost, which supports the page-level framing (a written page replaced by a fresh zero page) over an init-order one. (b) ⛔ **`vm/amap.c:amap_create()` is CLEARED as a suspect — do not re-walk it.** It looks wrong at first read: it does `*offset = *offset / SIZE_PAGE` and the whole amap API otherwise takes BYTE offsets (`amap_page`/`amap_clear` both do `offset / SIZE_PAGE` internally; `e->aoffs` is byte-based at every site in `map.c`, incl. `+= len` on entry split). But the division is only a scratch reuse of the caller's out-parameter to index the OLD amap in the copy loop, and the function **ends with `*offset = 0`**, which is the correct new value (the entry starts at the beginning of the freshly created amap). No early return sits between the two, so it is correct today — though reusing the caller's variable as scratch is fragile, and a future early return there would silently corrupt every later `amap_*` index for that entry. ✔ **That fragility is now removed** (kernel `ef4500cb`, 2026-09-25): the page-index scratch lives in a local, so the caller's byte-based offset is never transiently a page index. No behaviour change — C3 itself is unaffected and still waiting on a recurrence. ✔ **2026-09-25 — "ntpclient crashed" is NOT the same as C3; grade by the signature, not the victim.** The archive holds **four** ntpclient deaths and only **two** are this defect, so counting by process name would have inflated this row from 2 sightings to 4. C3's signature is a **read** fault at `far=0x30` (`esr=0x92000007`), and exactly two logs carry it: 2026-09-07 (`pc=0x41bfb4`) and 2026-09-15 (`pc=0x41bff4`) — so **"2 sightings, none since" stands**. The other two are different bugs. **2026-09-11** (`g-relF3-q2`) is a **write** fault at `far=0x0` (`esr=0x92000047`, `pc=0x4153c8`) that then storms — 2070 dump lines from one process — and is tracked nowhere; it is a distinct unresolved ntpclient crash, not evidence for C3. **2026-09-25** (`c1hpa01`) is a read at `far=0x5000` inside `malloc_heapSizeValid`, i.e. a C1-hunt *instrument* dereferencing an unmapped `live[]` entry — my own defect, fixed in libphoenix `819e461`, and never a C3 recurrence. ⚠ `pc` is not comparable across builds, so the signature is the `esr`/`far` pair plus the addr2line'd function name, never the raw address.

## C8

**Issue:** **A name on the NFS root intermittently stops resolving for a few operations, then starts again.** On 2026-09-23 three consecutive cases in the libc `stat_nlink_size_blk_tim` group each failed at their **first** resolution of the same relative path by name — `stat()`, `truncate()` and `lstat()`, all `Expected 0 Was -1` — while the two cases in between that touch a *different* name passed, and the group recovered by `st_dev_ino`. The file is created by the group's `TEST_SETUP` immediately after four `remove()` calls.

**Last measured:** **~1%, and NOT a regression** — 1 firing in 90 archived runs of the group (89 of them on the netboot NFS root); the same binary then passed 212/0 **twice** on the next boot. The earlier "regression since 2026-09-22" reading was a 1-vs-1 comparison against a single archived run and is withdrawn. **Two** nfs-fs mechanisms are eliminated **by reading**: the attribute cache is positive-only (`fe3979d`), so it cannot hide a file that exists, and `nfs_node_detachPath()` unbinds the name, so a detached node cannot shadow a fresh lookup. A **third is open** — `nfs_ops_unlink()` does drop a cached node for the path, but only *after* a `nfs_lstat64()` that, on **any** failure including a transient RPC error, returns `-ENOENT` at `nfs_ops.c:1206` and never reaches that code. The group's `TEST_SETUP` calls `remove()` on three names that are expected not to exist, so it takes that early return every time; whether a node bound to the path can survive it with a lazily-cached `fh` (the idle LRU keeps one at `refs==0`) is unread and is the next thing to check. Since 2026-09-23 the next firing is self-explaining: the setup's `open()` is asserted with its errno, and the failing case reports whether `fstat()` on that same descriptor still works — `fd` valid + `fstat` OK + by-name `ENOENT` would mean the inode is fine and the **name** is what went missing, the only outcome that points back into nfs-fs. Instrument verified against real syscalls on the host, both failure shapes and the healthy one.

## G3

**Issue:** **A stale Mesa shader-cache blob renders as green speckle** over an otherwise-valid frame. Phoenix has no ELF build-id, so the cache keys on shader source only and a host toolchain change invalidates nothing.

**Last measured:** **Mitigated, mechanism intact.** Both invalidation controls verified present 2026-09-22, and the `rsync --delete` hole that made the host-side one inert was closed 2026-09-16. No speckle report since. ⚠ The SD image ships **no** warm cache, so the first GL app on a freshly flashed card pays the full recompile. ✔ **2026-09-25 — the headline understates the protection, and it matters because it changes what work is worth doing.** The host-side control in `sync-netboot-tree.sh:99-115` does **not** rely on the hand-maintained `V3D_PHX_CACHE_VERSION`: it fingerprints the **sha256 of the three compiled Mesa archives** (`libv3d-phoenix.a`, `libGL-phoenix.a`, `libv3dv-phoenix.a`) and wipes the cache whenever that changes. That is **content-based**, so it catches exactly the case the headline calls unprotected — a host toolchain or sysroot change that alters the compiled driver without touching shader source — and it does not depend on anyone remembering to bump anything. ⛔ **Do not build a git-history or version-bump checker for this**: I wrote one, it reported "65 driver commits since the last bump" as a warning, and that was a **false alarm** — none of those 65 touched Mesa compiler sources (they are winsys/power/GPU-server glue), and the fingerprint would have caught it regardless. The tool was deleted rather than shipped.

## P3

**Issue:** **`dc zva` fast path disabled in `hal_memset` on the Cortex-A72.** Performance-only, correctness-safe. (TD-20)

**Last measured:** Open — but **no longer blocked on the EL2 question, which is now ANSWERED**. `tools/dczid-probe/` read `DCZID_EL0` on the real Pi 4: `raw=0x4`, **DZP=0 (dc zva PERMITTED)**, `BS=4` (64-byte block), and executing it zeroed exactly 64 bytes with the neighbouring byte intact. **`HCR_EL2.TDZ` is not set**, so the trap this row waited on does not exist. ⛔ Do not re-run that probe. ⚠ **The gate still stands for a better reason:** `hal_memset`'s own header says it *"may not work for uncached memory"*, and the recorded failure is a **hang with no exception output** in `_log_init`'s first large zeroing right after the D-cache is enabled — which fits `dc zva` on memory that is not Normal cacheable at that moment, not a trap (a trap would have raised an exception). ➡ Lifting it now requires showing **no caller of `hal_memset` can pass uncached memory** — a whole-kernel argument, not a measurement. Enabling it without that trades correctness for a perf-only gain, so it was deliberately left alone. ⚠ **2026-09-25 — the stated blocker may be the wrong frame for the recorded failure, which narrows the question but does NOT clear the gate.** The failure this row rests on is a hang in `_log_init`'s first large zeroing. That zeroing is `hal_memset(&log_common, 0, sizeof(log_common))` (`log/log.c:522`), and `log_common` is a **file-scope struct in ordinary kernel `.bss`** (`log/log.c:76-83`, dominated by `char buf[KERNEL_LOG_SIZE]`) — Normal **cacheable** memory once the kernel image is mapped, not Device and not Normal-NC. So "a caller passed uncached memory" does not explain *that* hang; the remaining suspects are specific to the moment it happens, i.e. the window immediately after the D-cache is enabled. ⛔ This is an observation from reading, **not** a reproduction and **not** a licence to lift the gate: the whole-kernel argument over all 108 `hal_memset` call sites (39 posix, 30 hal, 23 proc, 6 test, 4 vm, 3 log, 2 lib, 1 syscalls) is still owed, and the item stays perf-only with correctness risk. It does mean whoever picks this up should start by re-testing the `_log_init` window rather than auditing callers for uncached memory.

## P5

**Issue:** **Netboot NFS-root: one narrow boot-order race.** plo launches psh as a sibling of the NFS takeover without gating on it, so a command issued at the prompt can still hit the pre-takeover RAM root and report `not found`.

**Last measured:** Open; invisible in practice because the test harness waits for the takeover marker. ⚠ **2026-09-25 — the stated fix ("a plo boot-order gate") does not exist as described, and the obvious replacement is contraindicated. Read this before attempting either.** (a) plo's `app` lines only *register* programs in the syspage; `main.c:83-120` then walks that list calling `proc_syspageSpawn` back to back with **no wait between entries**, so `app` order is spawn order and nothing more. There is no bootloader-time wait that could gate it — `cmds/wait.c` runs before `go!`, i.e. before any program starts. (b) A real gate *is* constructible: `-x` sets `flagSyspageExec` (`plo/cmds/app.c:199`), which becomes the `X` the kernel tests, so dropping `-x` from the nfsroot psh line would load psh without running it, and the takeover server could then start it by name via `spawnSyspage()` (`libphoenix/include/sys/threads.h:60` → `syscalls_spawnSyspage` → `proc_syspageSpawnName`). ⛔ **But that makes the shell conditional on the takeover succeeding, and this project has already measured that class of change**: the `/etc/rc.nfsroot` (`psh -i`) indirection tried exactly that shape and was reverted because no-prompt boots went from **0 of 134 to 5 of 88** (rationale kept in `user.plo.yaml`). A boot with no shell costs far more than this race does. ➡ So the remaining options are an owner decision, not an autonomous change: accept the race, or gate psh and accept that a failed takeover leaves no shell.

## P7

**Issue:** **libphoenix has no UTF-8 support: the multibyte layer is C/POSIX byte-identity, so any text above U+00FF cannot be encoded at all.** Every conversion function maps one byte to one `wchar_t` (documented in a comment above each one in `wchar/wchar.c`). Measured on the host against glibc by `tools/libwchar-hosttest/` (4083 comparisons): `wcstombs` of a string containing U+1F600 returns **-1**; `mbstowcs("\xe4\xbd\xa0\xe5\xa5\xbd")` yields **6 wide chars, one per byte**, where UTF-8 would give 2; `wcwidth` reports **1 column** for East Asian Wide characters and emoji where glibc reports 2, so terminal alignment drifts.

**Last measured:** Open, and **newly written down rather than newly broken** — this is long-standing deliberate behaviour, not a regression. ✔ **What is NOT affected:** the same harness proves all 17 locale-independent functions (`wcslen wcscmp wcsncmp wcschr wcsrchr wcsstr wcsspn wcscspn wcspbrk wmemchr wmemcmp wmemset wcscpy wcsncpy wcscat wcstol`) match glibc **exactly, 0 differences** — the wide-string core is correct. ⚠ **Exposure is NOT audited per port.** It matters only where a port asks *libc* to convert; a port carrying its own codecs (CPython does) is unaffected. ✔ **`%ls` behaviour MEASURED end-to-end 2026-09-25** (not inferred), driving libphoenix's own `format.c` against its own `wchar.c`: `L"caf\u00e9"` emits `63 61 66 **e9**` — Latin-1, where UTF-8 would be `c3 a9` — U+00FF emits `ff`, and **U+0100 and above return rc=-1**. So the failure above U+00FF is LOUD (the whole `printf` call fails, which is correct C for an encoding error) rather than silent mojibake; below U+0100 it is silently Latin-1. That asymmetry is the thing to know before relying on `%ls` for UI text. Related: D3 (STK's wide-printf shim). ➡ Fixing means a real UTF-8 encoder/decoder in the mb* family plus a Unicode width table; both are self-contained and now testable on the host in ~1 s, so this is a well-bounded piece of work if the owner wants it.

## D3

**Issue:** **SuperTuxKart still carries its own wide-printf shim**, because Irrlicht passes `wchar_t*` to `%s` — which the standard defines as a **multibyte** string (`%ls` is the wide one). ✅ *Half of this closed 2026-09-23: libphoenix now implements conforming `swprintf`/`vswprintf`* (`libphoenix 07a0a29`, 11 target tests in `test-libc-printf`), so any other port needing wide formatted output just works.

**Last measured:** Open, and narrower than before. What remains is only STK's own non-conforming format strings: handing those call sites the conforming `swprintf` would reinterpret every wide string, so the shim now redirects by macro (`ports 6257d19`) instead of colliding with the real symbol. Closing it means changing Irrlicht's `%s` → `%ls`, not deleting the patch. ✅ **2026-09-24 — the printf half is now DONE too: `%ls`, `%lc`, `%S` and `%C` implemented** (libphoenix `21d3b32`, tests `42b9a0a`). `format.c` handled only `'s'`/`'c'`, and `l` before them merely set the 64-bit flag — so `%ls` read a `wchar_t*` as `char*` and printed `"L"` for `L"Lorem"`, stopping at the first zero byte. Silent wrong output for a standard conversion. New `FLAG_WIDE` + `format_printWide()`, converting via `wcrtomb()` in two passes (size, then emit) because the field padding must be known before the first byte and a wide string cannot be staged in the one contiguous buffer `format_printBuffer()` needs. Precision counts BYTES and never splits a character; an encoding error fails the call rather than truncating. **Gated both ways on hardware: 4/4 red without the change, 4/4 green with it; printf suite 129 → 133 tests, 0 failures; full libc sweep 1214 tests, 0 failures, 0 faults.** ⚠ **This does NOT let SuperTuxKart's shim go** — re-read the defect above: Irrlicht passes `wchar_t*` to **`%s`**, which is a *caller* bug, so a correct `%ls` does not help it. The shim stays until Irrlicht's call sites are fixed; what closes here is the libc gap, so any other port needing wide formatted output now just works. ⚠ The upstream `stdio_printf_cspn` `ls`/`S`/`C` cases stay ignored: they expect `L"\4399\0ns"` → `"#99"`, which needs a locale whose `wcrtomb()` can represent U+011B, and Phoenix's C locale is 1:1 onto bytes with `EILSEQ` above 0xff — a conforming implementation cannot produce that string. New standard-conforming cases were added instead.
