# Known open issues

Every issue we know about and have **not** fixed, in one list. Nothing else.

- **Open only.** A fixed issue leaves this file. Closed rows are kept, verbatim, in
  [`done/closed-issues-archive.md`](done/closed-issues-archive.md) so nothing is re-litigated.
- **No decisions recorded here.** Fix / postpone / won't-fix is the owner's call, made from this
  list; earlier verdicts have been stripped deliberately.
- **No history, and short.** Each row says what is wrong and what we last measured, in a few
  lines. Long-form notes live in [`known-issues-details.md`](known-issues-details.md) (one anchor
  per issue, linked from its row); an issue with a long investigation gets its own document —
  **C1: [`c1-heap-corruption.md`](c1-heap-corruption.md)**. Analyses live in `docs/misc/` and
  `docs/done/`.
- Open `TD-NN` transitional-debt items are issues too and are listed here.
  [`TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md`](TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md) keeps their
  engineering detail; anything marked RESOLVED there is not repeated here.

Verified against the tree, the git history and the boot-log archive on **2026-09-22**; cut back
to a register on **2026-09-26** (rows compressed, full text moved to the details doc, resolved
D3/D4/D6/D7/D8/D9 archived).

## 1. Correctness — crashes and data loss

| # | Issue | Last measured |
|---|---|---|
| C1 | **A stray 32-bit write of `0x80000000`/`0x80000001` lands at page+4** — in a malloc heap or chunk header, or (once) kernel memory. Usually a heap whose later `free()`s leak silently; at worst it crashes the app or **halts the kernel** (EL1 abort, 2026-09-26). Almost only in SuperTuxKart. Full record: [c1-heap-corruption.md](c1-heap-corruption.md). | **Open; root cause unknown, but now reproducible on demand.** Clearing the Mesa shader cache before a run makes it fire in 4 of 5 trials against 0 of 5 with a warm cache (cache→mode 10/10, 2026-09-26). Leading picture: a stale DMA pointer into a recycled contiguous block — all 12 victim physical pages sit in one ~5 MiB band just above `RAM_ADDR`, pending a control (build 3). ⛔ The old "`V3D_KEEP_CLOSED_BO` suppresses it" result does not survive the full archive. |
| C3 | **Two libc globals read back zero, killing the process at `main`.** `stderr` and psh's applet list are both unset, so `fprintf` dereferences a NULL `FILE*` (`far=0x30`). Both live in one 4 KiB `.bss` page. A source review gave a clean negative on every kernel mapping path, so "those writes definitely execute" is the assumption the next occurrence has to test. | **2 sightings (2026-09-07, 2026-09-15), none since**; only `ntpclient` affected. Signature is a read fault at `far=0x30` — grade by that, not by "ntpclient died" (2 of its 4 archived deaths are other bugs). [details](known-issues-details.md#c3) |
| C4 | **Intermittent V3D binner wedge on long GPU runs.** Auto-recovered by a GPU reset that reports loudly (`RENDER TIMEOUT` / `DROPPED job`). Not an MMU fault — a CT0 front-end stall with zero error status, `ct0ca` parked inside a valid BCL BO. `q3dm7` is the documented reproducer. | **Not seen since 2026-09-09.** 0 wedge signatures in ~136 800 GPU frames (to 2026-09-25), and the named reproducer `q3dm7` ran clean on a current build (8 655 frames). Diagnostics armed. [details](known-issues-details.md#c4) |
| C5 | **PWM audio DMA stalls at startup on some boots**, which used to hang Quake II inside `SDL_OpenAudio()`. Captured three times: the channel is alive but parked for a DREQ that never comes, ring full, 0 samples moved. Mechanism open. Blast radius is contained — the driver now grades the channel by progress, re-arms, and degrades to a paced null sink. | **Mechanism unfixed; symptom quiet.** 25/25 Quake II runs since 2026-09-18 reached `SDL audio initialized` and drew frames; 0 stall aborts in any log 09-19 → 09-22. ⚠ Timing-sensitive: the rate has moved across functionally neutral relinks, so short clean runs bound it rather than clear it. ✔ **2026-09-25 — +3 clean Quake II runs, graded with the driver's own literals** (copied from `audio/`, not composed): all three gate q2 runs show `SDL audio initialized` **present** (so the audio path was genuinely reached — the context is valid, not a silent log), with **0** `write STALLED`, **0** `engine RECOVERED after the stall`, **0** `paced null sink`. Running tally **28/28** reaching audio init with 0 stall aborts. ⚠ Unchanged conclusion: the rate moves across functionally neutral relinks, so clean runs **bound** this rather than clear it. |
| C6 | **psh forks `ntpclient` fire-and-forget on session start**, so a ~56-year wall-clock step can land anywhere in a ~2-minute window. Any app that measures a duration in *wall-clock* time across its own startup sees nonsense. | **The one app that ever failed this way is fixed; the systemic exposure remains.** ✅ quake3's `Sys_Milliseconds` now uses `CLOCK_MONOTONIC` (`ports fd34552`) — it was the only port glue still using `gettimeofday`; quakespasm, vkquake and sdl2 already used monotonic. The property is measured, not assumed: `tools/clockstep` steps the wall clock 56 years on hardware and monotonic moves by exactly the `sleep(1)` (`mono-delta 1000 ms` vs `real-delta 1766015999858 ms`). ⏸ Still open and owner-gated: making psh *wait* for the clock is what its comment says was tried and reverted, and a bounded wait delays the prompt on every cold boot on every target since `pshapp.c` is shared. Historical rate of a visible failure: ~1 in 174 quake3 runs. |
| C8 | **A name on the NFS root intermittently fails to resolve for a few operations, then recovers** (`stat`/`truncate`/`lstat` → `ENOENT` on a just-created file, 2026-09-23). | **~1 %, not a regression** (1 in 90 runs). Two nfs-fs mechanisms eliminated by reading; a third — `nfs_ops_unlink()`'s early `-ENOENT` return — is open. The next firing self-explains. [details](known-issues-details.md#c8) |

## 2. Graphics and UI

| # | Issue | Last measured |
|---|---|---|
| G1 | **Windowed GL in X11 is bandwidth-bound, ~10 fps.** A GL app drawing into a window copies pixels GPU → CPU → socket → CPU → GPU every frame: 96 ms/frame at 640×480, of which `XPutImage` is 58 ms. No DRI3/DMA-BUF equivalent exists, so a client can only hand the server pixels, never a buffer reference. Full-screen GL is unaffected (the games bypass X). | Architectural. All cheaper mitigations measured and closed; a point fix was half-proven on hardware with a ceiling of only ~1.7×. ✔ **2026-09-25 — the headline numbers are STALE. Re-measured at the SAME 640×480** (`gl-x11: start (640x480, …)`), agreeing across two independent showcase gates hours apart: **70.6 ms/frame, `put` 33.9 ms, 14.2 fps** — against the row's 96 ms / 58 ms / ~10 fps. So frame time is **1.36×** better and `put` **1.71×** better than written. ⭑ That 1.71× is exactly the *ceiling* this row attributes to the "half-proven" point fix, which suggests it landed and the row was never updated — **causation NOT verified**, only the coincidence is reported. Current breakdown: `put` 33.8 (48 %), `read` 12.5 (18 %), `pack` 6.4 (9 %), `draw` 1.6 (2 %), and **~16 ms (23 %) unaccounted** by the app's own counters — presumably server-side/socket, and the obvious next measurement if anyone revisits this. ➡ Plan against **14 fps, not 10**. |
| G2 | **xterm resize artefacts while dragging** on the GPU X desktop (owner-reported). | **Unreproduced.** No new evidence since 2026-09-14; resize *correctness* is verified once settled. The missing measurement is a deliberate drag test with the mouse released. |
| G3 | **A stale Mesa shader-cache blob renders as green speckle** over an otherwise-valid frame. Phoenix has no ELF build-id, so the cache keys on shader source only and a host toolchain change invalidates nothing. | **Mitigated.** `sync-netboot-tree.sh` wipes the cache whenever the compiled Mesa archives' sha256 changes — content-based, so a toolchain change is caught too. No speckle since 2026-09-16. ⚠ The SD image ships no warm cache. [details](known-issues-details.md#g3) |

## 3. Platform limitations

| # | Issue | Last measured |
|---|---|---|
| P1 | **Only the 4 GB Pi 4B is validated, and 2/8 GB boards are known to be mis-mapped** — plo's syspage memory map is still hardcoded. The DTB parser also assumes a single interrupt controller. (TD-06, TD-15 remainder) | Open. Do not simply try an 8 GB board. Also in TD-15: VC4 quiesce + mailbox-move (low value), and drivers use identity va2pa (⚠ do not naively wire `dtb_armToBus` — it would break GENET). ✅ **2026-09-25 — two 2/8 GB-board holes closed in passing** (devices `ec654c0`): both in-process VideoCore mailbox callers (`v3d_phoenix_power.c`, which is linked into **every GPU application**, and `v3d_gpu.c`) resolved the message page with `va2pa`, checked only the unresolvable case, then cast to `uint32_t`. A PA above 4 GiB was silently truncated, aiming the firmware at the wrong physical page — which it then writes its response word into at +4 — while still reporting success. `rpi4-vcmbox` and `rpi4-wifi` already guarded this; these two did not. Latent on the validated 4 GB board (highest PA in the whole log archive ~`0x451f0000`, and vcmbox's guard has never fired), real on 2/8 GB. |
| P3 | **`dc zva` fast path disabled in `hal_memset` on the Cortex-A72.** Performance-only, correctness-safe. (TD-20) | Open, perf-only. The EL2 trap question is **answered** (`DCZID_EL0` DZP=0 — `dc zva` is permitted). What remains is showing no `hal_memset` caller passes uncached memory, and the recorded hang may not be that at all. [details](known-issues-details.md#p3) |
| P4 | **The generic aarch64 early-console path hardcodes the UART at VA `0xffffffffffe00000`**, because it must print before the DTB-discovered base is available. On the Pi 4B this alias equals the discovered pl011 base. Matters only when porting to another aarch64 board. | Open for a future cross-board port; inert on this board. |
| P5 | **Netboot NFS-root: one narrow boot-order race.** plo launches psh as a sibling of the NFS takeover without gating on it, so a command issued at the prompt can still hit the pre-takeover RAM root and report `not found`. | Open; invisible to the test harness. ⚠ The "plo boot-order gate" fix does not exist as described, and gating psh on the takeover was measured to cost no-prompt boots (0/134 → 5/88) — an owner decision. [details](known-issues-details.md#p5) |
| P7 | **libphoenix has no UTF-8: the multibyte layer is byte-identity**, so text above U+00FF cannot be encoded (`wcstombs` returns -1 for U+1F600; `wcwidth` reports 1 column for wide glyphs). | Open; long-standing, not a regression. The 17 locale-independent wide-string functions match glibc exactly. `%ls` is silently Latin-1 below U+0100 and fails loudly above. Well-bounded to fix and host-testable. [details](known-issues-details.md#p7) |
