# Known issues and limitations

Open items in the Phoenix-RTOS Raspberry Pi 4 port, as of 2026-09-09. This is
the user-facing summary; the exhaustive engineering registries are:

- [docs/pi4-hardware-support-matrix.md](pi4-hardware-support-matrix.md)
  — per-peripheral status with evidence.
- [docs/TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md](TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md)
  — the `TD-NN` transitional-debt registry (its bottom "Tracking Checklist" is
  authoritative; most `TD` items are already resolved).

Resolved items are removed from this file as they are fixed, so it shrinks over
time; the git history keeps the record of what was fixed.

| atexit-null-head | ✅ **ROOT-CAUSED AND FIXED 2026-09-11** (was filed as an ntpclient bug; it is neither ntpclient's nor a network bug). A process died before `main()` with **2070 identical `Data Abort (EL0)`, `far=0x0`, `esr=0x92000047` (a WRITE)**, all at one PC. `/bin/ntpclient` and `/bin/psh` are **byte-identical** — it is psh under an applet name — so the unstripped `prog/psh` symbolises it: the PC is `memset` (`arch/aarch64/memset.S:113`, the `dc zva` bulk path) and **`lr` is `_atexit_init` (`stdlib/atexit.c:86`)**. The call is `memset(atexit_common.head, 0, sizeof(struct atexit_node))` with **`head == NULL`**. Arithmetic agrees: `sizeof` is 784, `dc zva` follows `subs x2, x2, #0x40`, and the dump's `x2=0x2d0`=720 is the remainder on the FIRST block. `head` is initialised statically, so NULL means the initialised `.data` word did not survive into the process image — it came from the address of a **file-scope compound literal**, leaving no named storage to recover to. ⓘ This file already noted `atexit_common` corrupting on this target, but only as observed at **exit** in `__cxa_finalize`; this is the same bookkeeping failing at **init**, so the two are worth treating as one problem. **Fix (libphoenix `160e916`):** the first node is now a NAMED static object and `_atexit_init()` re-points `head` at it instead of faulting. | **Fixed.** Verified in the generated code — `ldr x0,[x19,#8]` → `cbz x0` → `bl memset`, with that `bl` at the exact `lr` from the crash dumps — and on hardware (libc suites 93/0 and 2/0, 0 exceptions, 0 ntpclient faults). ⚠ The recovery branch only *fires* when `head` is NULL (~1 boot in 60), so the clean run shows the normal path is unharmed, not that the rare path is exercised; the argument for the repair is structural. **Still open, now narrowed to LOAD TIME (2026-09-11):** the ELF is correct — `atexit_common` sits in **`.data`** at `0x435ac8` and the bytes at `+8` read `e0 73 43 00 …` = **`0x4373e0`**, exactly `atexit_firstNode` (`.bss`, size `0x310` = 784, which also confirms the `sizeof` used above). So the initialised pointer IS in the image with the right value, and a runtime NULL means **`.data` did not reach the process intact** — not a compiler or linker fault. ⏭ Suspect the demand-paging path: `/bin/psh` is paged from the NFS root, and this codebase has already fixed one short-read defect there (`vm/object.c` `f145658f`, which left stale bytes in a page tail for demand-paged **text**). A `.data` page arriving zeroed would produce exactly this. ⚠ It would affect **any** statically initialised pointer, so it is worth more than the one crash it caused. ✅ **Mechanism now closed (kernel `6cd3adec`, boot-verified, pushed):** `object_fetchCluster()` treated a **premature EOF** — `proc_read` returning 0 before the object's declared size — as end-of-data and **silently zero-filled the page remainder**, exactly the shape that turns a valid `.data` pointer into NULL. It now retries up to 5× and prints the port/offset/byte-count if the read really is short, so the failure can no longer happen invisibly. On a healthy boot the diagnostic does not fire, so the *first cause* (why a read returns 0 early) remains open. |
| premain-hang | ✅ **ROOT-CAUSED AND FIXED 2026-09-11 — it was never a libc/pre-`main` bug.** An app intermittently failed to start, producing no further output and never returning psh's prompt. Storming the real binary (`/usr/bin/quakespasm -loadbench`, ~85 launches/cycle via `/bin/spawn-storm`) reproduced it **with the startup trace live**, and the trace settles it: **all 8 libc initialisers completed — including `file`, the `isatty`/`tcgetattr` suspect — and `main() entered` printed.** The process loaded the game and died in **V3D bring-up**, last line `v3d-coldstate: … meas=0 Hz … clkstate=0x0` (clock **off**). A stall, not a harness cutoff: 23 completed launches at ≤3095 ms = ≤71 s, while the command was still alive at the 300 s cap ⇒ **≥229 s hung**. **Mechanism:** the next statement reads **V3D core MMIO**, and a read of an unclocked block never completes; SError is masked here (**TD-10**), so there is no abort — the process hangs forever, silently. The clock was off because `v3d_phoenix_powerOn()` deliberately toggles it OFF/ON around the `PM_V3DRSTN` deassert through the **direct mailbox FIFO with the result discarded** (`(void)`), and that FIFO has **no hardware arbitration** — a concurrent client (vcmbox server, thermal, usb, genet) can pop the response. The **call site discarded the return too**, so a failed power-on walked into the hanging read. **Evidence picking out the clock:** of 7 anomalous cold-state readings, six were `0xffffffff`=`MBOX_FAIL` (the *query* failed) and none stalled; the single `clkstate=0x0` (query succeeded, clock off) is the one that hung. **Fix (`phoenix-rtos-devices` `9f9ec65`):** enable via the serialized `/dev/vcmbox` and **read the state back** with bounded retry; **check `v3d_phoenix_powerOn()`'s return** and bail `-ENODEV` rather than touching MMIO; report the retry count. | **Fixed, well-supported, not yet statistically proven.** After: **170 launches, 0 stalls, `clk=on` 170/170, 0 retries needed** — but that is only ~0.8 expected events at the old ~1-in-220 rate. What strengthens it: the *diagnostic* GET queries still use the racy direct FIFO and **still fail ~9% in the very same runs**, so contention is demonstrably live, yet the vcmbox-routed enable never needed a retry. ⏭ Only `quakespasm` is relinked against the fixed `libv3d`; the other four games still link the old archive (a GPU-archive change does **not** invalidate port state — force each port and require both a `Build state changed` line and the string in the binary). Detail: `docs/misc/2026-09-11-v3d-clock-race-mmio-hang.md`. |
| allocator-double-free | libphoenix's allocator reports a double free and the process exits **70** (`EX_SOFTWARE`). **Not AF_UNIX-specific**, which is how this row used to describe it: the report appears in **21 logs from 2026-06-28 → 09-09**, across **xcalc (×7), Dillo, vkQuake (×2), the glamor desktop / Window Maker / showcase (×5)** and `test-libc-unix-socket` (×4). It is a **generic heap-corruption symptom** with several distinct causes, some already fixed separately (the `vasprintf` overflow behind glib2/mc/Dillo; `free()` of `.rodata` in X11). Older logs say `Double free detected`, newer ones carry a named report. **Only ONE occurrence in the whole archive ever captured the block detail** (2026-09-09 `getname1`, `size = 0x410`); the other 30 predate the named report and carry no fields at all, so every inference below rests on a sample of one. ⚠ **Two readings this row used to assert are WRONG, corrected against the allocator source 2026-09-10.** (a) "un-coalesced, so both neighbours were in use" is impossible: `0x410` has `CHUNK_PUSED` **clear**, i.e. predecessor free, and `_malloc_chunkJoin`'s backward loop absorbs any such chunk before `free()` returns. Both flags clear is instead the allocator's own signature for *a header that was freed and merged away* and is now interior to a larger free chunk. (b) `hfree = 0xe40` in that same report puts used at 4080-3648 = **432 bytes, less than the block's 1040**, so the heap's own accounting says the block was **not live** — strong evidence against a live-block header smash here, but not proof: `freesz` lives at `heap+8` and is itself reachable by an underrun below the first chunk, so the books are only trustworthy if the same event did not clobber them. Do not treat this door as closed. ⚠ **And one of the three "eliminated" mechanisms is un-eliminated**: duplicate hand-out was refuted by a detector that *could not fire*, because it tested `CHUNK_CUSED` after `_malloc_chunkSplit()` had erased it (libphoenix `1ee441a`). Re-tested after repairing it: 1500 liveness children, 0 hits — that refutation is now sound. What survives: a stale absorbed header being re-freed, a stale pointer into a heap re-created at the same address, and a footer-planted header. Ownership audit of `resolve_path`/`unlink`/`sys_clear` is clean. | Open, rare; **no field occurrence since 2026-09-09**, and today's 64 cycles are clean. The report now names its **caller** plus the two **footers**, which discriminate the mechanism on sight: `foot == size & ~3` means the allocator wrote the header (a genuine double free), a mismatch means something else did (an overrun or a planted footer), and `pfoot` shows whether the chunk grid below is intact. HW-proven on both mechanisms — a deliberate 1-byte overrun reproduces `size = 0x410` exactly with `pfoot = 0x4141414141414141`. Resolve `caller=` with `addr2line` against the unstripped `prog/` copy. |

## System-level limitations

| Area | Limitation | Status |
|---|---|---|
| Board portability (TD-06) | The DTB parser assumes a single interrupt controller; only the 4 GB Pi 4B is validated (1/2/8 GB models untested). | Known limitation. |
| Early-console alias — cross-board port (B5) | The generic aarch64 early-console path (`phoenix-rtos-kernel/hal/aarch64/generic/console.c`, `_hal_consoleEarlyPutch`) hardcodes the UART at the fixed VA alias `0xffffffffffe00000` — it must print *before* the DTB-discovered base is available. On the **Pi 4B this alias equals the discovered pl011 base, so it is correct** and is intentionally left as-is. It only matters when porting to **another aarch64 board** (Pi 5, Pi Zero 2 W, other SoCs) whose console isn't at that alias: there, the early-print path must be conditionalized to use the board's discovered base, or early boot output goes to the wrong address. A source comment marks the exact spot. | **By design for the Pi 4; a to-do only for a future cross-board port.** |
| SError masked (TD-10) | Asynchronous SError is masked in early kernel paths because a live PCIe/VL805 USB external-abort SError is not yet root-caused; unmasking regresses boot. A dump-and-halt handler is implemented and armed for when the abort is fixed. | Known, HW-gated. |
| `hal_memset` DC-ZVA (TD-20) | The `dc zva` fast path is disabled on the Cortex-A72 pending proof of the EL2 DC-ZVA trap state (does not reproduce in QEMU). Performance-only; correctness-safe. | Known limitation. |
| Stack-exhaustion signal DoS | A userspace process that **exhausts its 1 MiB main-thread stack** takes down the kernel: fault-signal delivery (`hal_cpuPushSignal`, aarch64) writes the signal frame to the now-unmapped user stack and double-faults at EL1, with no recovery — so any program overflowing its stack crashes the box (register-confirmed via a stack-bomb repro, `tools/stack-bomb/`). Fix = a guarded signal-frame push (validate the target is in a writable mapped region before writing; terminate the process cleanly on failure), minding the demand-paged-stack case. **Attended** (highest-blast-radius kernel path — invisible to a green-boot smoke). | Known; turnkey work-order in [docs/done/2026-08-22-signal-push-stack-exhaustion-dos-workorder.md](done/2026-08-22-signal-push-stack-exhaustion-dos-workorder.md). |
| **Windowed GL in X11 is bandwidth-bound (~10 fps), by architecture** | A GL application drawing into a **window** on the X desktop copies its pixels **GPU → CPU → socket → CPU → GPU every frame**. Measured on the 640×480 demo window: **96 ms/frame (10.4 fps)**, of which `draw` is **2.7 ms** and the rest is the round trip — `glReadPixels` 12.5 ms, packing 6.7 ms, and **`XPutImage` 58 ms** pushing 1.23 MB through the X socket. Full-screen GL is *not* affected: the games bypass X entirely and render straight into the scanout buffer, which is why QuakeSpasm manages ~37-48 fps and Quake III 25-46 fps in the same build (both single
on-screen readings that vary with the view: Quake III reads 25 first-person on q3dm1 and 46 with the
showcase orbiting camera). **Root cause:** this port has no equivalent of DRI3/DMA-BUF, so there is no way for a client to hand the X server a *reference* to a rendered buffer — only the pixels. Contributing detail: there is no `resource_get_handle` (export) in this Mesa build, and MIT-SHM is not available (no shm, extension not built). Every cheaper mitigation has been measured and closed: a larger AF_UNIX ring (+12%, throughput flat at ~12 MB/s), poller contention (refuted), a cached alias for the readback (refuted — uncached DRAM is only 1.3× off cached), and deferring the present (no effect). | **By design for now — owner decision, 2026-09-09.** A point fix (passing a buffer handle over an X property) was designed, and two of its four pieces were proven on hardware, but it was **closed deliberately**: it would leave the port with no general buffer-sharing story, and its ceiling was only **~1.7×** (≈17 fps) because the DDX present — 1.74 ms + 0.07 ms/row, ≈35 ms for a 480-row window — survives the change. If this is ever worth paying for, the right investment is a **Phoenix-RTOS-specific DRI/DRM layer** that all clients and the server share, not a bespoke channel. Reference (not a plan): [docs/misc/2026-09-09-gl-window-buffer-sharing-work-order.md](misc/2026-09-09-gl-window-buffer-sharing-work-order.md). |
| **`std::chrono` had 1-second resolution** (toolchain) — **FIXED 2026-09-10** | libstdc++ here was built with **no time backends**, so `std::chrono::steady_clock` fell back to whole-second `time()`. It capped SuperTuxKart at exactly 1 fps and failed **silently** everywhere else. It turned out to be **~30 features off, not one**: `random_device` returned the same sequence every boot (mt19937 seeded 5489), `thread::hardware_concurrency()` returned 0 on a 4-core part, `filesystem::is_symlink()` was always false (`lstat` aliased to `stat`), and `last_write_time()` had 1-second resolution. ⚠ **The fix this row used to recommend (`--enable-libstdcxx-time=rt`) is wrong**: `=rt` appends `-lrt` and this target has no librt. Two causes, both silent — every probe is a C++ link test run *before* `libstdc++.a` exists (`cannot find -lstdc++`), and the clock probes are additionally guarded on `_POSIX_TIMERS`, which libphoenix does not define. Neither is fixable by a flag or a config cache. | **Fixed** — `phoenix-rtos-build` `gcc-16.2.0-12-libstdcxx-phoenix-features.patch` hardcodes the answers for `*-phoenix*`, as rtems/freebsd already do. HW-verified: `steady_clock` tick 1 s → **2 µs**, a 20 ms `sleep_for` really sleeps 20 ms (was 760 ms), `hardware_concurrency()` 0 → **4**. Audit: `docs/misc/2026-09-09-toolchain-silent-feature-audit.md`. |
| **SD boot of the current image is unverified** | The host card reader is **detached** (it shares the USB-C port with power/eth) and there is no card in the Pi, so the shipped image cannot be flashed or SD-booted on this bench — the owner is the first to boot it from a card. Substitutes in place: the contents gate now asserts the FAT boot partition (the six files the firmware needs, `arm_64bit=1`, and that every file `config.txt` names exists) and runs automatically inside `--variant sd`; plus a QEMU structural boot check. All other verification is netboot/NFS. | Known bench limitation; mitigated by gates, not by a boot. |
| Ethernet link IRQ (TD-Eth-LinkIRQ) | The PHY's `INT_B` line is not routed to a GIC SPI on the Pi 4 board, so link state is MDIO-polled at 1 Hz (as Linux/U-Boot also do). | By design for this board. |
| SD write throughput | Reads use UHS-I **DDR50** (1.8V) + **SDMA** + multi-block CMD18 (~38 MB/s, ~86% of Linux on the same card); writes are multi-block CMD25 but **PIO** (~17 MB/s DDR50 / ~13 MB/s HS50 — a BCM2711 controller quirk corrupts DMA writes, so they stay PIO). Multi-block writes verified 0-corruption. The 1.8V/DDR50 switch is reliable on netboot and best-effort on SD-boot (falls back to HS50). Remaining (attended) levers: DMA writes and reliable DDR50 on SD-boot. | Reads fast; writes correct but PIO-bound. |
| Audio | PWM audio over the 3.5 mm jack works with a streaming DMA ring and a Quakespasm mixer backend; an audible end-to-end sign-off on real headphones is still pending. | Partial. |
| Netboot NFS-root reliability | Over NFS root, an early command can hit the pre-takeover RAM root and report `not found` if `psh` starts before the NFS-root `takeover` completes (a boot-order race; the clean fix is a `plo` boot-order gate), and asset-heavy loads can see transient read failures in the NFS lease-reclaim window. Booting from the **SD/eMMC ext2 root** avoids both, and a **gigabit link** (now the default lab setup) greatly reduces the transient reads. | Known; use SD-boot or gigabit for asset-heavy workloads. |

## Partial / not started

- **WiFi (BCM43455) — data plane proven at FULL MTU in both directions; the
  lwip netif is the remaining integration step.** The driver
  joins a real WPA2-PSK access point, completes the 4-way key handshake, **and
  carries real traffic over the air**: it obtains a full DHCP IP lease
  (DISCOVER → OFFER → REQUEST → ACK, confirmed by the AP's `DHCPACK`) via
  `tools/wifi-probe jointxcnt`. Beyond that lease, the frame path now carries
  **full-size ethernet frames both ways**, verified byte-for-byte: the Pi sends
  400/1000/**1472**-byte UDP payloads that a host socket receives bit-exact, and
  reads back a host-sent 1472-byte tagged probe unchanged. Getting there needed
  two fixes — SDIO byte-mode CMD53 caps a transfer at 512 bytes (larger requests
  silently wrapped the 9-bit count field, so 525..2048 was a corruption band),
  and function 2's block size had never been programmed, which made block mode
  unusable on the data path. The driver now exposes `/dev/wifidata` (write a
  frame / read a frame) as the seam for an lwip netif. What is **not** wired up
  yet is that netif, so arbitrary sockets do not use WiFi and for everyday
  networking you should still **use wired Ethernet** (fully working).

  *Measurement note for anyone debugging this:* `tcpdump` on the host's AP
  interface does **not** see frames sent by the Pi — not even the DHCP that the
  host's own dnsmasq answers — so it is useless as an egress detector on this
  rig and has twice produced a false "no egress" conclusion. Use an
  application-level detector (a UDP socket, or dnsmasq's own logs);
  `scripts/wifi-air-monitor.sh` wraps the ones that work. (The earlier "TX reaches the firmware but
  not the air" report was a measurement artifact — a link-layer counter that
  doesn't count broadcast/pre-lease frames; the application-layer DHCP exchange
  is the ground truth.) The proprietary Cypress firmware blobs are **not
  vendored** in this repository (copyright/EULA hygiene);
  `scripts/stage-bcm43455-firmware.sh` stages them locally into a gitignored
  `.firmware/`.
- **Bluetooth (BCM43455) — driver-level bring-up only.** `/dev/hci0` comes up, the
  firmware patchram loads (323/323), a real BD_ADDR is read, and an HCI Inquiry
  completes. There is **no host Bluetooth stack** — no pairing, profiles, or audio
  — so it is not usable for real Bluetooth work yet.
- USB mass storage, I²C / SPI / PWM general-purpose drivers, and camera (CSI-2) /
  DSI display are not implemented.
