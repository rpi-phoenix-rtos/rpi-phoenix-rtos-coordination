# Known open issues

Every issue we know about and have **not** fixed, in one list. Nothing else.

- **Open only.** A fixed issue leaves this file. Closed rows are kept, verbatim, in
  [`done/closed-issues-archive.md`](done/closed-issues-archive.md) so nothing is re-litigated.
- **No decisions recorded here.** Fix / postpone / won't-fix is the owner's call, made from this
  list; earlier verdicts have been stripped deliberately.
- **No history, and short.** Each row says what is wrong and what we last measured, in a few
  lines. Long-form notes live in [`known-issues-details.md`](known-issues-details.md) (one anchor
  per issue, linked from its row); an issue with a long investigation gets its own document —
  **C1: [`c1-heap-corruption.md`](c1-heap-corruption.md)**. Analyses live in `docs/misc/` and
  `docs/done/`.
- Open `TD-NN` transitional-debt items are issues too and are listed here.
  [`TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md`](TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md) keeps their
  engineering detail; anything marked RESOLVED there is not repeated here.

Verified against the tree, the git history and the boot-log archive on **2026-09-22**; cut back
to a register on **2026-09-26** (rows compressed, full text moved to the details doc, resolved
D3/D4/D6/D7/D8/D9 archived).

## 3. Platform limitations

| # | Issue | Last measured |
|---|---|---|
| P1 | **Only the 4 GB Pi 4B is validated, and 2/8 GB boards are known to be mis-mapped** — plo's syspage memory map is still hardcoded. The DTB parser also assumes a single interrupt controller. (TD-06, TD-15 remainder) | Open. Do not simply try an 8 GB board. Also in TD-15: VC4 quiesce + mailbox-move (low value), and drivers use identity va2pa (⚠ do not naively wire `dtb_armToBus` — it would break GENET). The new GPU servers were not re-audited for physical addresses above 4 GiB (guards seen: `kms_bo.c:103`, `v3da_jobs.c:1444`); the 2026-09-25 mailbox fixes were in files deleted with the old stack. |
| P3 | **`dc zva` fast path disabled in `hal_memset` on the Cortex-A72.** Performance-only, correctness-safe. (TD-20) | Open, perf-only. The EL2 trap question is **answered** (`DCZID_EL0` DZP=0 — `dc zva` is permitted). What remains is showing no `hal_memset` caller passes uncached memory, and the recorded hang may not be that at all. [details](known-issues-details.md#p3) |
| P4 | **The generic aarch64 early-console path hardcodes the UART at VA `0xffffffffffe00000`**, because it must print before the DTB-discovered base is available. On the Pi 4B this alias equals the discovered pl011 base. Matters only when porting to another aarch64 board. | Open for a future cross-board port; inert on this board. |
| P5 | **Netboot NFS-root: one narrow boot-order race.** plo launches psh as a sibling of the NFS takeover without gating on it, so a command issued at the prompt can still hit the pre-takeover RAM root and report `not found`. | Open; invisible to the test harness. ⚠ The "plo boot-order gate" fix does not exist as described, and gating psh on the takeover was measured to cost no-prompt boots (0/134 → 5/88) — an owner decision. [details](known-issues-details.md#p5) |
| P7 | **libphoenix has no UTF-8: the multibyte layer is byte-identity**, so text above U+00FF cannot be encoded (`wcstombs` returns -1 for U+1F600; `wcwidth` reports 1 column for wide glyphs). | Open; long-standing, not a regression. The 17 locale-independent wide-string functions match glibc exactly. `%ls` is silently Latin-1 below U+0100 and fails loudly above. Well-bounded to fix and host-testable. [details](known-issues-details.md#p7) |
| P8 | **A client parked on a live but stuck server ignores `SIGKILL`.** Once a server has received a request, the sender sleeps uninterruptibly with no timeout until the reply, so killing a client of a hung driver does nothing (upstream FIXME in `proc/msg.c`). | Open, same code upstream. ✅ The *dead*-server half is fixed (kernel `38ad32cf`: the owner's exit fails every pending request with `-EINVAL`). Making the received state interruptible needs the server to learn about the abandoned request safely; design in [port-death.md §4](gpu-new-lane/port-death.md). |
| P9 | **`poll()` on a device-server fd is quantised to 20 ms unless the server opts in.** Any set other than a single inet socket sleeps `POLL_INTERVAL` (20 ms) between status queries, so an event wakes a poller 0–20 ms late. | Mitigated 2026-09-27: kernel `ee5939fc` adds `pollNotify(oid)` — a server that calls it on a readiness change wakes pollers in **38–62 µs** (single fd, next to a pipe, next to AF_UNIX; Pi-measured), and servers that do not are unchanged. Opted in so far: `rpi4-kms`. Still open: every other server (posixsrv, …) keeps the 20 ms quantum; ✅ signal reaction is immediate again (kernel `fb8b66ee`, `eintr set=server` 1000.1 ms). [poll-wake](gpu-new-lane/poll-wake.md) |
| P17 | **A default condition variable waits on `CLOCK_MONOTONIC`, not POSIX's `CLOCK_REALTIME`** (local revert `c283f2d` of upstream `4ab9ad9`, kept because the wall clock jumps 1970 → today at boot). POSIX-correct code that passes a `CLOCK_REALTIME` deadline to such a condvar waits ~56 years, i.e. until signalled. Found in SDL: `SDL_CondWaitTimeout`, so ffplay's `-autoexit` and a quit after EOF hung ([M10](gpu-new-lane/M10-video-player.md)). | Open, systemic. **Census 2026-09-29** ([doc](misc/2026-09-29-condvar-clock-census.md)): affected in the image: **Python 3.14 timed locks/events/queues** (parking lot), **every libstdc++ timed wait** (built without `_GLIBCXX_USE_PTHREAD_COND_CLOCKWAIT`), v3dv perf queries; SAFE = glib/GTK/XFCE, Mesa GL/wsi, SDL 0011 (`sdl2_kmsdrm`, in the default image). (The plain `sdl2` port is no longer in the image.) Clean fix: stop the boot-time wall-clock jump — C6 was closed by decision, not fixed, so that remedy lives here now; else a libstdc++ rebuild plus per-program patches. |
| P19 | **No file-change notification on Phoenix.** GLib has no inotify/kqueue backend and no polling fallback for directories, so `g_file_monitor_directory()` fails: Thunar views, xfdesktop and panel launchers do not refresh when files change (it was the `liblauncher-CRITICAL … Failed to start file monitor` line, now demoted to debug). | Open. Fix: a Phoenix polling `GLocalFileMonitor` backend in the glib patches (`gtk3_wayland`), or a kernel notification API. |
| P20 | **The hostname is empty and the resolver cannot answer for the local host** (no `/etc/hosts`, no "my hostname" answer), so `gethostbyname(gethostname())` fails: QuakeSpasm `UDP_Init: gethostbyname failed`, empty Quake 3 `Hostname:`. | Open. Fix: set a hostname at boot, and have `getaddrinfo`/`gethostbyname` answer `""`, `localhost` and the hostname locally (plus a shipped `/etc/hosts`). |
| P21 | **`MAP_SHARED` and `MAP_PRIVATE` are the same flag (both `0x0`, kernel `include/mman.h:28-29`)**, so a program cannot ask for a shared file mapping and gets whatever the kernel does for 0. Code that relies on writes through a `MAP_SHARED` mapping reaching the file or other processes (Mesa's disk cache, SQLite WAL, some IPC) cannot be told it is unsupported. | Open, found by the port audit. Needs a decision: real shared file mappings in the VM, or a distinct flag that fails loudly until then. [audit](misc/2026-09-30-port-feature-audit.md) |
| P22 | **No stack protector**: libphoenix has no `__stack_chk_guard`/`__stack_chk_fail`, so no port or core component can be built with `-fstack-protector-strong`. | **Runtime written** (libphoenix `cfab972` + test `38216d2`, branch `stack-protector`, lands in build 6); the guard seed is weak until the kernel provides random bytes (TD-28). Enabling `-fstack-protector-strong` comes next, network-facing ports first. [audit](misc/2026-09-30-port-feature-audit.md) |
| P23 | **Most autotools ports are built at `-O0`**: `phoenix-rtos-build/Makefile.common:160` exports `CFLAGS` to ports before the optimisation level is added (`:179`), and autoconf adds no `-O2` when `CFLAGS` is set. That covers libnfs (the NFS-root server), mbedtls, bash, freetype, fontconfig, libX11/xcb, pixman's C paths and xterm. | **Fixed in build 6** (phoenix-rtos-build `71b723d` + ports `7879360`; libnfs `nfs_get_readmax` is 3 instructions, libraries at 13–21 % stack slots). Measured on the Pi: **xz -1 on 64 MiB 122.5 → 61.5 s (2.0×)**; NFS read unchanged (28.4 → 28.6 MB/s, network/server-bound); sha256sum unchanged. Closes when build 6 is pushed. [audit](misc/2026-09-30-port-feature-audit.md) |
| P24 | **Every `malloc()`/`free()` costs two syscalls** — libphoenix's allocator takes a kernel mutex on every call, and `mutexLock`/`mutexUnlock` have no user-space fast path (~4.5 µs per pair on the Pi). A bash loop iteration makes ~81 heap calls, so it costs ~380 µs (200 000 iterations: 76 s; Linux: well under a second). Every program pays this. | **Cause found** (code read + host call counts, 2026-10-01). Fix 1 in progress: skip the malloc lock while the process has one thread (as glibc does). Fix 2, a user-space fast path for every mutex (a syscall only on contention), speeds up everything but changes a core primitive — **owner decision**. |

It polls with an idle back-off instead: fast (200 µs) while frames flow, up to 10 ms when idle.
